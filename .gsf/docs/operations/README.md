# Evidence custody, resource limits and interruption recovery

Use the existing coordinator, job/event lifecycle and [worker contract](../../agents/WORKER_CONTRACT.md); these procedures add no scheduler, storage service or alternate approval path. Read accepted [policy](../../state/config-contract.md), [environment](../../state/environment-contract.md) and, when relevant, [release](../../state/release-contract.md) contracts. Runtime evidence belongs to the authorized job or its approved store, not distribution source. No secret, credential file, browser profile or private chat export belongs in ordinary artifacts.

## Establish an evidence store before relying on it

Policy `evidence` declares `store` (`job`, `ci`, `external`), `retention_days` and `location`. Declaration alone proves neither access nor durability. The coordinator records a custody/retrieval index in the job's authorized evidence, with an owner and each required artifact's job/candidate/policy identity, exact immutable locator, SHA-256 digest, byte length, media type, creation/observation time, retention deadline, classification, reader/writer roles, sanitization relation and retrieval receipt. Use the contract evidence-reference shape `{locator,digest,observed_at}` wherever a schema requests it; this index is supporting evidence, not a new canonical state schema. Never put access tokens or expiring signed query strings in a locator. Keep the stable object/version/artifact identifier instead and retrieve with the caller's existing authenticated tooling.

1. Resolve `job` location from the repository root (normally `.gsf/jobs`); reject escaping/overlapping protected source storage. For `ci`, identify the actual provider, repository, run and artifact ID, not “latest successful.” For `external`, identify the accepted tenant/bucket/container/object version and existing provider tools. A filesystem directory, CI artifact or URL is not automatically backed up or immutable.
2. Establish classification and authentic access authority. Ask the actual storage administrator/operator for the approved readers, writers, deletion rights, retention/legal-hold controls and retrieval path when they are not discoverable from authorized platform settings. Read actual ACL/IAM/run-access evidence through existing tools; record a sanitized receipt. Do not broaden ACLs, enable public links or probe using another person's credentials. Platform permission changes require their own scoped authorization.
3. Retrieve a known non-secret object through the actual intended reader context, using the existing filesystem, CI artifact-download UI/CLI or provider object-download interface. Record exact command/UI action and principal role, timestamp, exit/result and immutable locator. Hash the retrieved bytes and compare with the recorded digest. A listing or HTTP success alone does not prove the bytes, correct artifact or later reader access. Test a denied/unprivileged context only through an authorized existing test identity; otherwise report the negative ACL proof unestablished, never attempt credential theft.
4. Inspect actual retention configuration. Confirm the required deadline is covered by the CI expiration/object lifecycle/backup policy and that necessary readers retain access. For manually managed local jobs, name the custodian, preservation/backup destination, review date and deletion procedure; label retention **manual**, not TTL-enforced. Ignored local files can vanish on workstation loss or removal. If required durability exceeds the available controls, stop claiming it and obtain an approved durable store.
5. Preserve upload/copy, settings, ACL and retrieval receipts in the index. Store to the accepted location only under write authority; read-only discovery may inspect an existing artifact but must not create a sentinel. When no existing harmless object or test identity is available, request an authorized custody exercise; do not mark the store verified without it. An unavailable store blocks every gate relying on its evidence, not unrelated inspection.

### Digest and sanitization procedure

Hash **bytes**, not a prettified YAML object, excerpt, rendered page or newline-normalized copy. On systems with existing tools, `sha256sum <actual-file>` (POSIX) or `Get-FileHash -Algorithm SHA256 -LiteralPath <actual-file>` (PowerShell) is a read-only hash recipe; substitute an authorized actual path and retain its command/result. If the tool is unavailable, discover an existing equivalent; do not invent a hash or install a helper silently.

- Capture raw tool receipts into an access-controlled transient or approved restricted store where authorized. Filter secrets at collection where possible. Do not first leak raw secrets to a public log and then call a redacted copy safe.
- When raw retention is permitted, hash exact raw bytes, retain them under restricted ACLs and record a separate `raw` locator/digest. Produce a sanitized retained receipt, hash its exact bytes, and record a distinct `retained` locator/digest plus redaction categories, method/tool/version, operator and time. A raw digest is never proof that sanitized bytes are identical. Each evidence reference points to the digest of the bytes retrievable at **that** locator.
- If raw bytes may not be retained, record their non-retention/disposal reason and the sanitization method. A raw digest may be recorded only if policy permits it and it was actually measured; a hash of low-entropy secrets can itself leak information. Record no raw locator or retrieval claim after disposal. If a required proof depends on unavailable raw content, the proof remains blocked; reacquire a safe equivalent with authorization rather than fabricate a receipt.
- Contract identities requiring raw canonical bytes (for example a frozen `environment.md` digest) must stay exact. Sanitize before freezing that file. Never replace its bytes after acceptance while preserving its identity; create a new observation and invalidate/rebind affected evidence through the normal lifecycle.
- A digest detects byte changes; it is not a signature, authentic operator grant, independent review or proof of who produced the bytes. Provenance and source authentication need actual platform controls and receipts.

### Retrieve during checks, review, release or incident

Resolve references from the accepted job's index, authenticate through existing approved controls, download/read the exact version into an authorized isolated destination, recompute digest, inspect identity/time/classification, and record the retrieval result. Verify that candidate/policy/environment/target bindings and expiry still match the claim. Missing object, access denied, expired artifact/link, digest mismatch, altered ACL, insufficient retention or an ambiguous “latest” locator is a precise blocker. Preserve the failed receipt, stop the affected approval/action and notify the coordinator/custodian. Do not silently choose a different run, regenerate a passing receipt, weaken access controls or treat a local cached copy as the missing durable artifact. Reacquisition gets a new evidence identity and fresh required review.

### Retain, extend and dispose

Before closing/removing a job, confirm the required artifacts are retrievable for the full accepted period, legal/incident holds, relevant review principals and recovery needs. If the period exceeds provider maximums or access expires sooner, obtain authorized export to an accepted store, preserve source/destination digests and copy receipts, then perform retrieval from the destination. Do not delete the sole copy during migration. Record custody changes without rewriting old receipts.

At the deadline the named custodian checks holds and accepted retention authority, enumerates exact owned versions/copies and requests scoped deletion where required. Delete only authorized expired evidence; preserve audit metadata according to its own classification/retention rules. Record actual deletion/platform lifecycle results, not a promised cron job. If deletion cannot be verified, report residual copies/owners and escalate. Never delete canonical active job data, source, unrelated logs, platform backups or legal-hold material through a blanket cleanup. [Removal](../guide/README.md#remove-gsf-safely) must preserve required evidence first.

## Reasoning preference is not a resource limit

Optional `models.md` reasoning `budget` expresses preference only. `inherit`, `small`, `medium`, `large` and `unlimited` are not token entitlements, money, wall time, host quotas, parallelism or permission grants. “Unlimited” never overrides accepted `execution_limits`, provider rate limits, sandbox boundaries, required reviews or operator authority. Use only actual advertised effort controls/models and record effective settings or that no corresponding control exists; do not derive model slugs or arbitrary token counts from these labels.

Before dispatch, the coordinator reads accepted `execution_limits`: cap live tasks at `max_parallel_tasks` including existing workers; count attempts without observable progress against `max_attempts_without_progress`; track actual elapsed time against `max_elapsed_minutes`; establish how `max_cost` and `currency` are observed. Count objective progress (new reproducible evidence or an accepted completed unit), not repeated retries, unchanged output or a new model's confidence. Record timestamps, attempt/progress receipts and known live ownership at checkpoints. Use real host/CI/platform bounds where available; Markdown declarations do not enforce them.

`max_cost` is a nonnegative **integer in the currency's ISO 4217 minor units**, or null; USD values are cents, not floating-point dollars. Record actual currency exponent and meter-to-policy-unit conversion receipts. Unknown/nonmonetary currency, an ambiguous exponent, incompatible/unobservable conversion or an unobservable required cap cannot pass. Keep policy fingerprint inputs exact strings/integers/booleans/null, never float/nonfinite values. `max_cost: null` means cost unknown/unmetered, not free. A required cap needs real accounting/control with the right scope (all workers, model calls, tools and external costs relevant to the accepted cap), lag/overshoot characteristics and currency. A provider's estimated API-only budget is not an exact hard all-in cap; subscription quota is not a monetary meter. If the required cap cannot be observed/bounded to accepted policy, block affected execution and seek authentic policy/limit authorization; never invent usage telemetry or convert quota messages into a cost estimate. Host quotas may fail earlier than policy limits. No periodic quota polling, reset time, automatic wake or continuing supervisor is established by these instructions.

## Actual quota, tool failure or limit checkpoint

On a real quota/rate-limit/unavailable-resource response, capture its sanitized actual wording, tool/request identity, time, exit/status and retry information **only if supplied**. Do not infer reset time or promise automatic resumption. At policy expiry/no-progress/elapsed/cost boundary, stop new dispatch/effects even if the host still works. Retry only after an observed changed prerequisite and within remaining accepted limits; never rotate accounts/models to evade restrictions.

1. Follow [pause-safely](../../skills/gsf-mode/playbooks/pause-safely.md). The coordinator records in the exact authorized job checkpoint: job/event/plan/candidate/policy and active-instruction identities; repository/worktree/branch/HEAD and dirty/untracked owned paths; completed units and unrun/failed/stale obligations; exact evidence/index locators; actual resource failure and known limits; current worker/process IDs, ownership, liveness and outstanding remote intents/receipts; precise blocker, next safe action and required resume authority. Workers report only their owned evidence to the coordinator.
2. Stop, await or fence owned writers using the real host/platform controls and retain acknowledgements. An ended chat or missing heartbeat does not prove an agent, CI run, shell, cloud operation or deployment stopped. If cancellation cannot be confirmed, record liveness unknown and block overlapping ownership or retry. Preserve external-resource ownership and compensating/recovery actions; do not leave unrecorded running writers.
3. Persist the checkpoint and needed receipts to the accepted store; retrieve/hash them if capability remains. If the tool failure prevents a durable write, report the exact unpersisted information/location to the operator through an available authorized channel. Do not claim it was saved. A returned tool call does not imply a future worker will wake.
4. Report BLOCKED/SUSPENDED under existing lifecycle semantics, current safe product state, evidence location, unresolved operations and exact prerequisite. A proposed time to check manually is not a scheduled task. Scheduling a future invocation needs an actual supported service, explicit authorization, owner, task receipt, lifetime/cancellation and verification; absent these, manual authenticated re-invocation is required.

## Cold resume acceptance

An operator/authorized caller names the **exact existing job** and invokes [session pickup](../../skills/gsf-mode/playbooks/session-pickup.md). The coordinator must retrieve checkpoint, accepted frozen policy/instructions and indexed evidence; validate schema versions under that job's frozen contracts; reconcile invocation receipts, worker/process liveness, complete events, accepted decisions, plan and actual workspace/remote state before any effect. A generic “continue” or recent conversation selection is not proof of correct job identity.

Reobserve host versions/permissions, required capabilities and target identity/freshness using [host adapters](../hosts/README.md); do not silently refresh the accepted instruction snapshot or reinterpret a legacy job. Establish that quota/tool availability actually returned using an authorized minimal discovery or required operation, without asserting a quota reset. Obtain authentic renewed authority before exceeding elapsed/no-progress/attempt/cost limits or expired grants. Reconcile uncertain remote actions by inspecting actual target/forge state before retry; preserve deduplication/idempotency and recovery requirements.

Resume acceptance requires retrievable matching artifacts, known/fenced non-overlapping ownership, resolved actual blockers, current prerequisites, sufficient accepted limits/grants and explicit next eligible DAG action. Missing checkpoint, mismatched digest, unsupported frozen schema, stale identity, live unknown writer, unresolved remote effect or unavailable mandatory resource leaves the affected work blocked. A new candidate/environment observation invalidates affected checks/reviews through the existing lifecycle; neither restart nor READY converts old results into fresh approval.

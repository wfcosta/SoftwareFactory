# Cloud composition

## Trigger and accepted boundary

Use for an accepted infrastructure/IaC, IAM, network, managed-service or environment-operability change or assessment. Inspect real trust boundaries and provider resources; a cloud filename is not sufficient classification. This is an informational composition, not a policy profile, configuration schema, installer, cloud client or permission declaration. Packaging it grants no credentials, tools, hooks or effects.

A direct read-only question inspects existing permitted material and returns chat only: no jobs, files, runs, endpoint calls or experiments. An execution assignment must separately authorize observed targets and actual effects. A reviewed plan, approval, configured check, credential or local default context is not apply authority.

## Ordered conditional flow

1. Coordinator routes the existing assessment/change playbook and applies every [impact matrix](../skills/gsf-mode/references/impact-matrix.md) surface. Record affected IaC modules/configuration, IAM principals, network paths, data/service dependencies and exact external resources. Continue authorized design if execution prerequisites are absent, but keep dependent claims blocked.
2. Discover actual supported provider/IaC tooling and product runbooks. Observe authenticated principal/account/project/subscription, region or evidenced provider-specific absence of region, cluster/namespace, immutable resource IDs, backend/workspace and current state generation/fingerprint. Inspect inherited endpoint/profile/provider aliases and nested modules without disclosing secrets. Re-observe before critical effects and after context or credential change.
3. Freeze acceptance and actual resource ownership, permitted actions, effect/target declarations, scoped grants, genuine platform restrictions, time/resource/cost bounds and stop/recovery owner. State who can halt an operation and how. A Markdown lock or account label is not fencing or isolation; missing required real safeguards blocks execution.
4. Build the real immutable reviewed plan/configuration bundle with provider/module versions, source/configuration identity, state fingerprint and expiry. Review additions/deletions/replacements, effective privilege changes, dependencies and recovery limits. Stale plan/state, unknown identity, conflicting ownership or unexpected destructive delta stops the affected effect; do not silently replan and apply under an old review.
5. If accepted work is plan-only/verify-existing, report its bounded inspected facts without apply. If environment apply/deploy/recovery is separately authorized, use release purpose B and canonical deployment records; cloud-only artifacts bind actual immutable desired-configuration/plan provenance, not an invented image. Registry-only publication instead uses purpose A and requires no fake deployment/health evidence. Source merge is neither publication nor deployment.
6. Execute only the granted operation and resource scope. Capture native operation identity and reconcile actual remote status after timeout/cancellation before retry or cleanup. Exercise accepted allow/deny connectivity, privilege and service behaviors. Independently review actual diagnostic, operator handoff and recovery evidence through operability-reviewer; this role does not acquire release or performance authority.
7. Coordinator promotes owned receipts into existing environment/release/evidence records. Required code/security and applicable surface review plus all configured checks remain gates. Only separately authorized release execution can advance deployment, and only the accepted complete observation window can establish health.

## Positive/adverse proof and resources

- Positive: actual authoritative identity/state/lock reads; reviewed plan and resulting exact resource/configuration readback; required connectivity and least-privilege allowed path; correlated signals and actual responder/diagnostic route where accepted.
- Adverse: select denied principal/tenant/network path, stale-plan or wrong-target rejection, authorized bounded failure, unavailable dependency or recovery interruption according to impact. Never inject a fault merely because the pack mentions it. Prove accepted stop, reconciliation and recovery outcomes against real controls; a green IaC exit or dashboard screenshot alone does not establish them.
- One execution/resource owner per actual account/region/resource/backend lease; name cross-account IAM, DNS, certificates, secrets, shared network and replicas when touched. Builder owns assigned product/IaC paths; independent reviewers do not edit/apply their reviewed implementation. Coordinator alone owns canonical lifecycle/environment/release records. Capture/reset/cleanup/recovery are separately scoped effects; delete only owned resources after evidence retention.
- Real prerequisites include authorized supported provider console/API/CLI, IaC engine/provider versions, state read access and native locks/fencing, action-specific IAM rights, scoped authentic factory grant, operation lookup, signals/traffic controls and recovery interfaces for the accepted claim. No installations, account creation, backend initialization, credential switching or automatic network access are implied. Required unavailable target identity, observability, enforceable containment or recovery leaves the exact dependent step BLOCKED.
- Cost observations require real meter/currency conversion, delay and scope evidence when a cap applies; unknown/unmetered is not free. If a required cap cannot actually be enforced or observed as required, block execution instead of inventing a cost estimate as proof.

## Evidence and gates

Preserve original failed/completed attempts, actual command/API/cwd/version, candidate/policy and source/configuration/plan/state identities, expiry, native operation receipts, expected/observed resource state, grants references, sanitized signals and residual-resource ownership. Store retrievable immutable receipts with actual ACL/retention and raw-versus-retained digest provenance; no tokens, private keys or credential-bearing plan dumps. Configuration/state/provider/identity/plan/target changes invalidate dependent evidence and approvals.

Use existing report and release/environment schemas and `review-operability.md` as an additional accepted-plan report, not a new configured reviewer enum. Static review proves inspected properties only. Missing proof is BLOCKED, unexecuted proof is NOT RUN, and original adverse findings persist until resolved against their criteria. Independent non-author operability review supplements rather than replaces security, code, performance or release gates.

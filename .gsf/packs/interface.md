# Interface composition

## Trigger and accepted boundary

Use for an accepted browser/desktop UI or CLI/TUI consumer-task change, or bounded assessment of its visible behavior, accessibility and supported platforms. Include loading, failure, empty and recovery states when relevant; not every task needs both graphical and terminal drivers. This is an informational composition, not a configuration profile, installer, permissions grant, schema or bundled executable. Host packaging makes entries discoverable without granting capabilities.

A direct read-only question uses existing permitted evidence and returns chat without jobs, files, app launches, runs or experiments. Executing a journey needs explicit assignment for app setup, actions, actual effects/targets, captures and cleanup. Browser or terminal access does not authorize purchases, sending messages, production writes or destructive actions.

## Ordered conditional flow

1. Coordinator routes the existing feature/bug/review/verify-existing playbook and applies the whole [impact matrix](../skills/gsf-mode/references/impact-matrix.md). Inspect actual routes/screens/commands, supported platform/browser/terminal versions, neighboring paths, product requirements and external state. A UI-only label cannot waive API, data, privacy or release impact.
2. Where accepted into the plan, acceptance-challenger independently challenges proposed/accepted specification before build: actor, starting conditions, goal, failure/recovery behavior, accessibility and observable acceptance. Return proposals to the legitimate acceptance owner; the challenger cannot make its preferred behavior accepted or approve its own authored specification. Keep ambiguity and missing acceptance explicit rather than quietly adding product scope.
3. Freeze a finite journey/state/platform set from actual supported promises. Name real initial data, role/tenant, flags, locale, viewport/device or terminal dimensions, clock where relevant, expected visible outcome and important adjacent flow. Select control-ui for graphical surfaces, control-cli for command/terminal surfaces, both only when the accepted journey crosses both. Document justified omissions without dropping required gates.
4. Discover actual launch instructions, available host browser/desktop/PTY controls and supported versions. Bind the real candidate/build and readiness, URL/window/terminal process, working directory, owned profile/fixtures and reset/cleanup scope. Inspect startup/install scripts and nested effects before running; an existing terminal is not isolation and loopback does not imply harmless local effects. Missing private device/access, real UI controls or supported runtime blocks those claims rather than authorizing a mock.
5. For a bug, preserve the original real failing sequence before implementation where assigned and feasible; missing baseline stays explicit. Builder owns only assigned source and fixture resources. Execute the accepted actual journey through accessible controls or real terminal input. Capture expected versus visible/printed output, exit/status and resulting state; internal state alone cannot prove a user's visible result.
6. Exercise the chosen adverse and neighboring flow, then repeat the original failure after the fix. Review independent UI/UX evidence on the exact candidate; route localization to the existing i18n specialist when applicable. Mandatory code/security, configured checks and every other applicable reviewer remain required; this table is not the full policy reviewer list.
7. Preserve receipts and stop only owned tabs/processes/resources. Coordinator promotes worker reports and updates canonical records; reviewers do not repair their own reviewed candidate or claim implementation authoring as independence.

## Positive/adverse proof and ownership

- Positive graphical proof: real navigation/input/submit and actual expected visible outcome at recorded route/state/dimensions; matched reference and candidate conditions for visual parity; keyboard/focus and required semantics/assistive path for accepted accessibility claims.
- Positive CLI/TUI proof: real documented invocation or keystrokes, stdout/stderr or rendered terminal, exit code and resulting file/network/data state. A successful help/import command does not prove a changed command or terminal interaction.
- Adverse evidence: choose relevant invalid input, denied role/tenant, empty/loading/error/recovery, cancellation/retry, narrow viewport/terminal resize, locale/RTL/formatting or assistive path. Preserve console/network failures and downstream state where relevant. A screenshot cannot establish keyboard reachability; an automated accessibility scan alone cannot establish the complete assistive journey; one OS cannot certify all supported platforms.
- One builder owns source paths and named accounts/tenant fixture IDs, profile/data directories and app processes. Name external resource and recovery owners for form submissions, exports or other durable effects. Reviewers own assigned reports only. Coordinator owns accepted spec/plan/environment and canonical evidence. Stop/reconcile uncertain submissions before retrying; cleanup cannot erase required proof or affect unrelated user state.
- Prerequisites are actual app/runtime/driver versions, real UI/PTY controls, authentic scoped access, ready candidate, permitted test identities/data and bounded capture/reset/cleanup authority. Do not install dependencies, drivers/plugins, create accounts, borrow administrator sessions or fabricate captures to conceal a missing prerequisite. Continue independent reachable work while required missing surface proof remains BLOCKED.

## Evidence and retained gates

Retain the original and repeated action sequence, actual route/command/cwd, candidate/policy/build/configuration, fixture/user role/platform/locale/dimensions, timestamps, expected/observed output and sanitized captures/state receipts. Preserve failed and completed attempts with immutable retrievable evidence, actual ACL/retention/expiry and distinct raw/retained digests. Redaction must preserve the ability to assess the predicate without exposing credentials or sensitive user data. Changed build, flags, role, data, driver/platform or accepted behavior invalidates dependent evidence.

Use existing reports and `acceptance-review.md` for the additional accepted-plan role; no new policy reviewer enum or lifecycle schema. The challenger's PASS/CHANGES/BLOCKED assesses specification quality, never implementation success or owner acceptance. Executed per-predicate failures/inconclusive results remain explicit. NOT RUN and missing required proof do not pass; static review does not claim clicks, accessibility or consumer completion. Publication, merge and deployment still need their separate authority and evidence.

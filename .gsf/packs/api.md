# API composition

## Trigger and accepted boundary

Use for an accepted change or assessment to a public/service API, SDK boundary, webhook or event contract. Start from actual consumers and wire behavior, not the presence of an OpenAPI file. This is a finite informational composition, not an executable workflow, configuration profile, installation recipe, permissions declaration or new schema. Loading or packaging it grants no action authority.

A direct read-only question inspects existing permitted material and answers in chat: no job, files, endpoint calls, runs or experiments. Execution requires accepted scope and separately authorized effects. Verify-existing does not authorize fixing a discovered defect.

## Ordered conditional flow

1. The coordinator routes the existing feature, bug, review or verify-existing playbook. Inspect request, actual provider/caller graph, authoritative contract revision, supported/dormant consumers, policy and configured checks. Apply every row of the [impact matrix](../skills/gsf-mode/references/impact-matrix.md); a pack label cannot waive cross-domain work.
2. Freeze accepted consumer predicates and exact support directions: old consumer/new provider, new consumer/old provider or another promised combination. Record absent/null/default behavior, errors, pagination, authentication, tenant scope, retry semantics and deprecation windows only where affected. Conflicting contract authority or unknown support remains unresolved, not unsupported.
3. Have api-contract propose the protocol/coexistence design. Use contract-drift for a named observed-contract mismatch; retain the original clause and finding. If intent must change, seek authentic acceptance rather than regenerating the contract to match the implementation. Use compatibility-check only for required combinations, not all historical versions.
4. Assign implementation paths and real provider/consumer resources to one builder per exclusive scope. If events/webhooks are touched, additionally name producer, consumer, queue/subscription, dedupe store, DLQ and replay owner. If storage, broker IAM, privacy or rollout is affected, route those impact rows before execution; this composition supplies no deployment shortcut.
5. Freeze verification-strategy predicates, fixtures, identities, adverse cases, actual invocations, effects/targets, limits and recovery ownership before authorized execution. Execute the real supported provider and representative consumers. A generated client build, schema check or provider-authored mock cannot establish consumer behavior.
6. Required independent reviewers assess the exact evidenced candidate. Keep all configured checks and mandatory code/security review, plus applicable surface reviewers. A designer/author cannot supply their own independent approval. The coordinator alone promotes dispatch evidence and updates canonical lifecycle records.

## Proof, ownership and prerequisites

- Positive evidence: real accepted request/response bytes and consumer-visible result at exact provider, schema, client/runtime and configuration identities; required negotiation/coexistence direction; durable effect where promised.
- Adverse evidence: select relevant malformed/missing/unknown input, wrong scope/tenant, expired or tampered message, timeout and retry cases. For async claims, exercise duplicates/reordering and crash across acknowledgment/effect boundaries; observe dedupe, bounded retries, poison-message handling and authorized replay. A rejected HTTP request alone does not prove no downstream effect: inspect the owned observable state.
- The coordinator owns accepted spec/decision/plan/environment/candidate records and indexed evidence. Workers own only assigned product paths, dispatch receipts and explicitly leased fixture resources. api-contract does not edit product source. Independent reviewers do not implement repairs. Name cleanup/reconciliation owners for uncertain deliveries; do not blindly replay a timed-out effect.
- Discover actual installed HTTP/protocol clients, schema validators, real SDK/runtime versions, authenticated permitted provider/consumer fixtures and supported capture tools from product runbooks/help. No fictional commands, implicit network permission, dependency installation or credentials from this pack. Missing consumer artifact, endpoint access, safe isolation, target identity or replay authority blocks the corresponding proof and dependent claim; continue independent authorized analysis.

## Evidence and gates

Preserve original and failed attempts, exact invocations/cwd, candidate/policy/build/config/fixture identities, expected versus observed predicates, sanitized payloads/state and immutable retrievable receipt locators. Distinguish raw from retained digests, retrieval permissions and expiry. Redact credentials and sensitive payloads without claiming redacted bytes equal raw bytes. Source, schema, consumer, auth, configuration or fixture changes invalidate dependent proof; rerun or justify exact reuse.

Use existing report and lifecycle contracts, not pack-specific fields or verdict enums. NOT RUN is not PASS; unavailable required proof is BLOCKED; an observed violation remains a failure/finding until genuinely resolved and re-evidenced. Static contract review establishes only inspected properties, not delivery, compatibility or deployment. Publication, merge, deployment and health remain separate authorized and observed states.

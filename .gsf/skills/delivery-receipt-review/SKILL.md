# Delivery receipt review

## Role

Make an exact outcome recoverable to its intended reader without mistaking publication or transport acknowledgment for delivery or acceptance. Reuse [navigable delivery](../navigable-delivery/SKILL.md), [worker contract](../../agents/WORKER_CONTRACT.md), [candidate/evidence](../../state/candidate-contract.md), [environment](../../state/environment-contract.md), [evidence operations](../../docs/operations/README.md) and [authorization review](../authorization-review/SKILL.md). This is not a messenger, artifact backend, durable outbox or notification service.

Direct review returns no-write chat. Dispatch writes only its assigned Markdown assessment. Publishing, sending, granting recipient access, opening private content, tracking reads and cleanup are separate native effects requiring authentic authority and existing tools; this procedure performs none automatically.

## Context

Freeze one accepted purpose/outcome, authentic owner, exact original content/artifact revision and independently accepted whole byte identity where required, approved recipient/principal/channel/device/thread, current disclosure/retention policy, source-to-derivative provenance and actual existing delivery protocol/account/instance/version. Link genuine native intent/send/message/artifact/receipt identifiers to the existing task/occurrence without inventing IDs or a new canonical record format.

Require finite payload/artifact/page/attempt/time/cost limits, exact desired delivery predicate and deadline, current artifact custody/ACL/recovery controls, approved receipt privacy and authentic send authority. Use only explicit approved material/metadata; do not scan contacts, private inboxes, histories, credentials or provider accounts to locate a recipient or lost receipt.

## Task

### 1. Prepare the complete, readable and authorized object

1. Verify the accepted source/artifact and actual whole content identity against the intended outcome. Preserve original versus sanitized derivative bytes/pins and required material; a title, thumbnail, preview or summary cannot stand in for requested full evidence. Missing complete object blocks a complete-delivery claim.
2. Bind the exact intended recipient identity and approved destination, not a mutable display name or a convenient public channel. Check actual account/tenant/thread/device and current access through the existing authorized owner. Sender access is not recipient access; an unguessable/signed URL is not proof of correct ACL or safe disclosure.
3. Require the intended authorized reader can retrieve the exact whole version for the accepted decision/recovery window, with actual existing retention/custody controls and readback where required. Ephemeral spill storage, an expiring link or an unavailable recipient-read facility leaves that predicate unproven. Never fix denial by making the object public or disclosing credentials.
4. Check content, attachments, filenames, previews, URLs and notification metadata against accepted audience/region/data-handling limits before first egress. Authenticated URLs and secrets must remain in their approved custody; an authorized derivative has new provenance. Native pre-egress protection is a real control prerequisite, not a final-response wording filter.
5. Record prepared object/recipient/channel identity and immutable intended send content in the existing approved evidence. Preparation proves no send, delivery or acceptance. If full material cannot fit native bounds, use only an already approved recoverable artifact route; do not silently truncate or rerun the producer to obtain another copy.

### 2. Send only through the existing authorized protocol

1. Require authentic current authority for this exact payload, recipient, destination, classification and effect. Outcome completion or repository merge does not authorize a new external disclosure. Consent, policy, native permissions and current resource ownership are independent requirements.
2. Inspect the real native client's send/receipt/idempotency/reconciliation semantics and current version. Use existing genuine intent/deduplication/outbox controls when required, with original identity/readback before the effect. Do not invent endpoint fields, receipt status values, a queue or an exactly-once key.
3. Under separate exact authority, the existing sender invokes that interface once with the unchanged reviewed payload and destination, retaining actual native submission/message/artifact identity and timestamp. A tool return or HTTP success must be labeled only as the stage its documented contract establishes.
4. Missing stable identity, authentic authority, required pre-egress/custody controls, admission exclusion or durable prior-send history blocks the dependent send. No alternate provider/channel, new account, broad permission, fresh ID or unreviewed payload is a fallback.

### 3. Interpret each actual receipt at its own stage

| Actual evidence | Honest established fact | Not established automatically |
| --- | --- | --- |
| Prepared object and recipient map | Proposed complete payload and intended destination | Submitted or delivered |
| Native submission acknowledgment | Exact native service accepted the request under its documented semantics | Recipient device delivery, readability or absence of duplicate effects |
| Native delivered receipt | That exact message reached the documented recipient/channel stage | Human reading, whole artifact retrieval or comprehension |
| Native read/open observation | Only the documented identity/scope/time observation, if permitted and authentic | Informed acceptance, current artifact bytes or downstream action |
| Intended-reader whole retrieval/readback | Exact object/version recoverable to that authorized reader within the observed scope | Future retention beyond actual controls or acceptance of its claims |
| Authentic recipient decision over exact material | Only the separately bound decision and authority actually recorded | Execution success, legal rights, publication/merge/deploy or later business outcome |

Keep producer-issued identifiers, observed source time and local capture time distinct. Do not manufacture a delivery/read status from a screenshot, chat text, blank error, badge, public link, repository publication or another recipient's receipt. Keep sensitive tracking metadata private and require its legitimate purpose/retention. An absent receipt is UNKNOWN, not rejected or unsent.

### 4. Reconcile uncertain delivery before retry or cleanup

1. If acknowledgment/receipt is lost after possible submission, preserve the original intent, exact payload/destination, native IDs where actually returned, owner and prior evidence. Mark delivery uncertain; do not rerun the producer, silently resend, change message ID or select another channel.
2. Through separately authorized existing native exact-message/intent state, reconcile whether this original delivery occurred and what the protocol can prove. If original correlation is unavailable, name that prerequisite and keep overlapping resend blocked. A local missing record is not proof of non-delivery.
3. Duplicate notifications/results correlate to the same original native event where supported; do not double-count delivery or cost or infer duplicate production. Recovery reuses an established original receipt only after binding/custody checks, never synthesizes one from expected values.
4. Cancellation, queued-message removal and remote content deletion are separate supported effects with their own authority/readback and residual-copy limits. A local note deletion, sender-process exit or cancellation request cannot undisclose a delivered object or prove remote erasure.
5. Retain complete original receipts/material under actual approved access and retention before disposing only separately authorized disposable owned state. Preserve legal holds, user content and ambiguous operations; the native sender/artifact/access/recipient custodian owns missing evidence and recovery.

## Constraints

No sending, native account/credential discovery, read tracking, provider/model call, message service, outbox/backend/runtime/repository creation or automatic cleanup. Markdown enforces no recipient ACL, redaction, durability, idempotency or receipt authenticity. Source publication, delivery, read access, authentic decision and business acceptance remain separate. Changed payload/recipient/version/channel/grant/native contract invalidates affected readiness; never repurpose an old receipt.

## Format

Return the [assigned response](../../templates/response-template.md) or no-write chat: exact purpose/source/derivative/artifact/native/canonical identities; recipient/channel/current access and whole-read/retention evidence; authentic separate send authority and actual supported protocol/controls; per-criterion predicate/actual receipt/MET–NOT_MET–BLOCKED; prepared/submitted/delivered/read/retrieved/accepted facts separately; actual actions versus NOT RUN, unresolved original sends and consumed limits; custody/retention/invalidation/recovery owner and next safe action. A completed review is not a completed delivery.

Illustrative cases, NOT RUN: a PR is actually merged but the intended recipient has no artifact access—publication is established, delivery/readability is not. A native send times out after possible submission—reconcile the same intent before resend. A delivered message has a now-expired artifact link—do not claim complete recoverability. A read receipt is not approval of a destructive action.

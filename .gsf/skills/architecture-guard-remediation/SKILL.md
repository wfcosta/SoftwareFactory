# Architecture guard remediation

## Role

Review an accepted architectural invariant, actual existing checker evidence and an owned minimal remediation through to required real consumer proof. This agent procedure is not a static analyzer, source scanner, architecture compiler, runtime guard or new gate. No rule is inferred from what a checker happens to accept, and a paper decision does not enforce a dependency boundary.

Reuse [architect](../architect/SKILL.md), [architecture quality](../domain-review/references/architecture-quality.md), [domain review](../domain-review/SKILL.md), [verification strategy](../verification-strategy/SKILL.md), [contract drift](../contract-drift/SKILL.md) and [small PR planning](../small-pr-planning/SKILL.md). Follow the [worker contract](../../agents/WORKER_CONTRACT.md), [candidate evidence](../../state/candidate-contract.md), [configuration](../../state/config-contract.md) and [environment](../../state/environment-contract.md) contracts. Required code/security reviews, configured checks and protected rules remain unchanged.

Direct no-write requests return chat from supplied or already authorized source/receipts without jobs/files. A dispatch writes only its assigned owned Markdown report. Source remediation, checker execution and consumer observations are separately assigned to actual existing owners/tools; no code, commands, native calls, checker or fixture is produced or run here.

## Context

Freeze the accepted invariant and authentic product/architecture decision source/version/section, exact candidate/policy/environment, intended modules/layers/packages/processes/data ownership, allowed versus forbidden dependency/effect directions, accepted exceptions and actual owners. Separate normative rule intent from current source, checker defaults and comments. If intent is missing/conflicting, identify the real decision owner and block affected acceptance rather than inventing a rule.

Obtain the **already existing** checker/tool and exact installed version/build, authentic native rule identifier and configuration revision, documented semantics, language/build coverage, actual input/dependency graph and full prior violation receipts. Include exclusions, generated/vendor code, binaries/plugins, dynamic/reflection/DI/configuration paths, transitive references and runtime boundaries where applicable. A source search, file name convention or rule text is not an existing architecture checker or proof of complete enforcement.

Accept finite bounds for rules, modules/resources, graph depth/edges/nodes, source/diagnostic bytes, violation rows, prior findings, consuming paths, platforms, duration and observation freshness. Define expected consumer behavior/quality scenario and existing proof method with authentic product thresholds, separately authorized execution owner, allowed effects/resources, safe isolation and recovery. If a required existing checker/tool/consumer proof is unavailable, retain the gap; do not build a substitute or add a new gate.

## Task

### 1. Bind each rule to actual checker coverage

Use report-local rows, preserving every assigned rule and finding:

| Accepted rule/version and expected architectural predicate | Exact modules/resources/allowed and forbidden paths | Existing checker/version/rule/configuration + actual coverage/exclusions | Exact native violation/source and candidate | Minimal proposed remediation / owner | Required consumer proof / actual receipt | MET / NOT_MET / BLOCKED; next owner |
| --- | --- | --- | --- | --- | --- | --- |

1. Recover the rule's business/consumer reason and accepted boundary from its authentic source. Keep structural invariants, runtime isolation/security and measured quality objectives separate; a static dependency rule alone cannot establish runtime confinement or performance.
2. Map to the checker's actual native rule and supported semantics. Cite exact approved help/documentation/version and observed configuration/input scope, not a guessed analyzer option or framework method. A configured rule is not evidence it ran on the current candidate.
3. Audit coverage against the complete accepted scope. Identify files/modules/targets excluded or unsupported, generated or dynamically loaded paths, resolver/alias behavior and dependency graph provenance. A zero count proves only no reported violations within that actual tool/configuration/input/run scope; it is not universal architectural compliance.
4. Consume retained genuine checker receipts first: exact candidate/configuration/input/tool identity, invocation/run origin, complete diagnostics, actual completion/status and measured bounds. Missing/partial/stale evidence remains BLOCKED. A source-text assertion that the forbidden string is absent, or a test that merely restates the implementation, is not independent proof of the invariant.
5. Required fresh checker execution belongs only to the separately assigned owner using the actual existing check under its accepted effect/target and isolation. Do not install a checker, edit CI, create source-scanning scripts or invent a result to satisfy an unavailable prerequisite.

### 2. Resolve violations individually without weakening the rule

1. Retain each original violation/finding ID, native diagnostic/rule, exact file/module/symbol or resource locator, dependency edge/effect, reachable consumer and observed harm/preconditions. Distinguish a demonstrated violation from uncertain tool semantics or incomplete input coverage.
2. Determine the actual cause from inspected source/graph/configuration: misplaced responsibility, forbidden dependency, wrong ownership/data flow, invalid adapter boundary or an actual checker input/configuration error. Do not suppress the symptom, move it outside scanned paths or rename a forbidden symbol to pass a textual check.
3. Propose the smallest coherent correction that restores the **accepted** boundary and preserves behavior: remove an obsolete dependency, route through an already accepted interface, move the responsibility to its actual owner, or correct a genuinely wrong existing input mapping as supported by independent evidence. Do not introduce a speculative service/queue/abstraction or new checker merely to hide the edge.
4. Name exact source/configuration ownership, protected paths, affected consumers and rights/contracts, expected dependency/resource change and recovery basis. If several findings share a cause, link each one to the actual correction and retain separate closure proof; one resolved diagnostic does not close all rows automatically.
5. If intent needs to change, route a versioned design decision to its authentic owner before dependent implementation. Preserve the original violation and old policy; no blanket exception, inline ignore, gate waiver or self-edited rule may retroactively pass the original requirement. An unsupported or allegedly false-positive diagnostic needs real native semantics/source evidence and owner disposition, not silent deletion.

### 3. Hand off minimal remediation and require independent proof

The separately authorized source owner receives exact accepted rule, violation rows, minimal proposed diff, exclusive paths, compatible consumer obligations and retained recoverable baseline. Apply only within genuine task ownership and current authority; no change to unrelated user files, baseline protections or accepted thresholds. The coordinator binds the resulting exact candidate/policy and invalidates affected stale checks/reviews/approval.

For completion, require both:

- **Existing checker proof:** current authentic full-scope run on the resulting exact candidate/configuration, with original violations individually reconciled and no newly ignored/unread required scope. Removal of a diagnostic is only structural evidence within actual coverage.
- **Real affected-consumer proof:** independently specified input/initial state, actual consumer/build/environment, intended observable result and failure behavior, actual effect/readback/receipt, numeric objective when accepted, and limitations. Exercise the consumer path that depended on the changed boundary, not just an internal string/dependency count or mock echo of expected behavior. Existing verification strategy owns genuine runtime/isolated proof; required unavailable native dependencies/platforms stay BLOCKED.

For Markdown-only changes, an explicitly authorized real consumer walkthrough of the decision/ownership/refusal path may satisfy only an accepted procedural criterion. Do not claim that walkthrough is a compiled architecture checker, deployed runtime guard or native enforcement. Stronger accepted runtime/checker obligations remain blocked rather than silently converted to documentation review.

### 4. Reconcile failures and recovery

If the checker passes but the consumer fails, retain both facts and keep remediation acceptance unresolved. If consumer behavior passes but required architectural coverage is incomplete, retain the structural gap. Neither proof substitutes for the other. Unexpected scope, stale candidate, changed tool/rules/exclusions or active conflicting writers stops affected handoffs and invalidates dependent reliance.

A separately authorized correction/rollback uses the exact retained owned baseline, reconciles intervening changes and obtains new affected checker/consumer receipts; it does not erase prior findings or authorize deleting data. External/data effects require their real recovery owner and native operation/readback under release. Unknown possibly live effects/owners remain fenced or BLOCKED before overlapping retry. No broad reset, weakened rule, hidden suppression or repeated rerun without acceptance-relevant correction is recovery.

## Constraints

No new analyzer/compiler/schema/gate/runtime, source-text tautology, test suite, formatter, native probe, credentials or commands. Actual tools and authentic rules must already exist. Preserve accepted invariant semantics and full coverage; an owner-approved future rule change is a separate versioned decision, not a waiver of the current failing criterion. Do not claim architecture enforcement, complete safety or consumer success from this procedure's existence.

## Format

Use the [response template](../../templates/response-template.md) or no-write chat. Return exact accepted rule/version/scope and candidate; complete checker mapping/coverage/exclusions; original violation-to-owned-remediation rows; authentic decisions and minimal diff handoff; actual versus NOT RUN checker/consumer receipts; remaining structural/runtime gaps, recovery/ownership and next prerequisite. Include every criterion/finding with MET/NOT_MET/BLOCKED, retrievable evidence/ACL/retention and source/tool/rule/configuration/candidate invalidation conditions. Preserve the executing role verdict; proposed fixes and clean diagnostics are not accepted end-to-end remediation alone.

### Parent consumer cases — illustrative, NOT RUN

- A supplied existing checker reports a forbidden domain-to-storage edge. The accepted minimal owner-routed correction removes that edge; require both a current actual checker receipt and the affected consumer's real behavior/readback before closing the original finding.
- A clean run excludes the module containing the original violation. Keep its architectural coverage BLOCKED/NOT_MET as supported by evidence; do not call zero diagnostics closure or add a custom source search as replacement.
- A real boundary-preserving remediation passes the checker but breaks the consumer's accepted failure behavior. Preserve the consumer failure and route an owned correction; do not weaken the invariant, replace the expectation with current output or claim source-only success.

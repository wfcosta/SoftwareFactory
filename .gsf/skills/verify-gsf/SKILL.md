# Verify GSF

## Inputs and authority

Read the requested scope, repository-root-relative `.gsf/GSF_CONFIG.md`, the configured constraints/worker contract, the [scenario matrix](references/scenarios.md), and its [operational recipes](references/operational-scenarios.md). Read the seven canonical state contracts in repository-root `.gsf/state/` and apply [verification-strategy](../verification-strategy/SKILL.md) to accepted task-matrix rows in `decision.md`/`spec.md` under the [impact-routing reference](../gsf-mode/references/impact-matrix.md). Missing/invalid canonical policy grants no authority; never fall back to an old root-level policy. Use real host filesystem, shell, delegation and forge capabilities; no GSF executable or scheduled service exists. This skill is an assignable `kind: skill` check, not permission to edit policy or publish.

A structural check alone is not complete behavioral verification. Declare `complete framework core`, `focused structural`, or an exact named behavioral scenario set before execution. Report each requested scenario NOT RUN, PASS, FAIL, BLOCKED or INVALIDATED with actual receipts; distinguish trusted reused evidence from newly executed evidence. Never turn an unexercised case into PASS. Run checks only after writers finish. Keep all scratch products outside the source repository; no products or executable validation scripts are installed into GSF.

## Structural pass

1. Inventory delivered source files, excluding Git internals and narrowly ignored runtime evidence. In the distributed GSF repository, require `README.md` as the only root project file and `.gsf/` as the only project directory; `.git` administration stays intact. All other delivered project files, including policy, guides and docs, belong under `.gsf/`. Every operational framework file must end in `.md`; `.gsf/.gitignore` is the explicit Git exception, with ignore patterns scoped relative to `.gsf/` and narrowly excluding local runtime evidence without hiding policy/source. Reject a root `.gitignore`, bundled executables, generated test products, duplicate legacy formats, and operational names inherited from another product. Preserve truthful source provenance and license text. This distribution layout requirement does not require moving a host product's unrelated files when GSF is embedded.
2. Parse every skill's YAML frontmatter with an available parser. Require matching directory/name and a nonempty scalar trigger description. `disable-model-invocation` is optional, not a required GSF field; if explicitly present it must be a YAML boolean and cannot grant execution permission. Missing invocation metadata is valid and does not prove automatic host registration. Check that all skill-relative Markdown references resolve. Inspect semantic references and role names too, not just hyperlink syntax.
3. Read the single canonical YAML policy block and all seven single canonical JSON Schema blocks: `config-contract.md`, `plan-contract.md`, `event-contract.md`, `models-contract.md`, `candidate-contract.md`, `environment-contract.md` and `release-contract.md`. Use a real available strict YAML parser and Draft 2020-12 validator; absent tools block validation, not a visual substitute. Reject duplicate YAML keys, multiple canonical blocks, non-finite/unsupported scalar types, malformed booleans, unknown fields, repository-escaping paths and missing mandatory checks/reviewers. Current policy version is `2.0.0`, candidate version 2, environment/release version 1; other versions follow their actual contracts. Frozen accepted old jobs use their frozen schemas/instructions, never silent reinterpretation.
4. Validate distributed policy and every newly added/changed canonical example with its own schema, including synthetic environment/release examples; label synthetic identity/receipts as non-live. Derive negative copies from valid parsed data, change one field at a time, and require validator rejection: unsafe path, string permission boolean, empty checks, missing reviewer, invalid task status, missing lifecycle dispatch, wrong report origin, invalid model panel/pool, missing check `effect`/`target`, unknown effect/target, negative limits/retention, malformed target identity, unsupported version (policy `99.0.0`, other records 99), incomplete candidate collection/workspace and missing release provenance/artifact/transition receipts. If a rule is semantic rather than schema-expressible, record the actual semantic rejection separately rather than falsely claim the schema rejected it.
5. Exercise semantic checks independently: DAG/sender authority, path containment through real links/junctions, model entitlement, check effect/target versus nested actual effects, environment expiry and accepted/observed target equality, release state/transition/receipt consistency, immutable artifact/build/config/source lineage and authentic grants. A schema-valid account string is not observed authority. Validate exact evidence index/retrieval/ACL/retention proof; missing/expired content blocks the dependent gate.
6. Verify all five role pillars and all 23 playbook categories. Walk actual routes for new behavior, read-only investigation, unavailable delegation, pause, resume and publication denial. One normative worker/policy contract governs them; copied or conflicting rules fail this check.

## Launch / doctor / drive

1. Allocate an owned scratch repository with a real small CLI or other available surface and documented runtime. Copy the actual GSF instructions and create an accepted product policy there; no copying local jobs or private model preferences. Record fixture root, exact source/candidate/policy identities and actual host/tool versions in the environment record. Classify each configured check's `effect` and `target`; inspect setup/nested/capture/cleanup effects, not labels alone. External effects require accepted observed target, authentic scoped grant and real safeguards. A local invocation uses null target.
2. Establish readiness with the actual runtime and meaningful product checks. Distinguish application readiness from a process merely existing. Initialize a concrete job, then cold-resume it without overwriting evidence. Also exercise customized policy/agent/skill/template/job paths with default copies absent.
3. Follow the real coordinator → intake → specification → builder → checks → independent code/security review → approver sequence. Use separate actual worker contexts for implementation and independent review, record host handles plus GSF IDs, inspect their artifacts, and do not substitute a throwaway simulated dispatcher for real dispatch. Coordinator-permitted serial roles must be labeled honestly; required independence still needs an independent context.
4. Drive the changed CLI/API/UI path yourself and execute every configured check with its exact command/cwd or skill path and actual readiness predicates. Capture invocation, actual loaded build/artifact/config, fixture, output/exit status and source snapshot before/after. Use the candidate contract's bounded collection and isolated external export/build-input/output/artifact manifests for scalable builds; never hide unexpected in-repository content with blanket ignores. Require reviewer PASS and approver APPROVE for the same candidate/policy. With publication disabled, the positive result is approved local handoff and no external action.
5. Exercise the matrix's negative and interrupted-state cases against actual on-disk artifacts. Preserve baseline evidence, perturb only owned scratch copies, follow reconciliation, and record dispositions. An executable scratch probe may assist observation but does not establish an installed enforcement runtime.
6. Exercise support-skill semantics from the matrix on concrete inputs: previous-answer rewrite, prompt sharpening without execution, verify-map maintenance, recall privacy, reflection proposal-only behavior and truthful source-comment review. Record the actual result, not source-text keyword matches. Exercise optional platform/media/formal-check capabilities only with a real available tool; otherwise list them as not exercised rather than covered by the CLI.

## Evidence and cleanup

Record host/runtime versions, scenario, concrete input, candidate/policy identity, actual command or task receipt, expected/observed behavior, outcome, and limitations in a Markdown report. Evidence-only appends must not alter candidate identity; source additions/edits/deletions must. Updated instructions, check/toolchain/config/fixture inputs and expired environment/plan identities invalidate dependent results under verification-strategy. Trusted unchanged evidence needs its exact dependency/provenance/content/retrieval proof; a passing badge or matching HEAD is not sufficient.

Use the configured `evidence.store`, `location` and `retention_days`, job-local ignored Markdown by default, and exact evidence allowlist/index. Actually retrieve retained artifacts under an authorized proof-reading identity, compare digest/content, observe ACL/expiry/retention mechanism, and repeat after teardown and cold resume. Local manual retention is manual, not an enforced TTL. Missing/expired/denied/tampered evidence blocks its gate even if candidate is unchanged. A requested committed report contains sanitized durable results and reproducible fixture/task instructions; do not publish private paths, secrets or invented retained links. Destroy only owned scratch processes/directories after preserving receipts; never Git metadata, user worktrees, unrelated processes or evidence.

## Gate and output

Return declared scope, scenario/obligation table, newly executed versus reused versus NOT RUN, actual evidence, gaps and final PASS/FAIL/BLOCKED. `Complete framework core` PASS requires every structural/boundary/semantic step, F01–F10/F12 lifecycle cases and the core operational contract cases specified in the matrix; unavailable core delegation/review is BLOCKED. A focused PASS names only the exercised subset and cannot satisfy the complete configured verify-gsf gate unless the accepted policy explicitly calls for that exact focused scope. Required domain/surface rows additionally block their dependent readiness when unproved. Optional live cloud/publication/media/formal/OS cases stay explicit NOT RUN/BLOCKED capability limits unless required; CLI coverage never implies those surfaces passed. No universal or permanent reliability guarantee is implied.

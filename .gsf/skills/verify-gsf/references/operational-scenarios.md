# Operational regression recipes

These are specifications for real host-executed disposable fixtures, not claims of executed tests. Build or adapt fixtures only in owned directories **outside** GSF source using an actually available runtime and dependencies. Do not add applications, test executables, IaC or dependency files to the distribution. Record NOT RUN until an invocation occurs; report PASS, FAIL, BLOCKED or INVALIDATED using [verification-strategy](../../verification-strategy/SKILL.md). Each recipe must exercise GSF's actual accepted policy, coordinator decisions and receipts as well as the product predicate. A toy application passing alone does not prove orchestration.

## Common execution contract

1. Freeze a per-run binding table in the external fixture's Markdown evidence: fixture source/digest, real runtime/tools/versions, absolute owned fixture root, source/candidate/policy IDs, exact executable invocation and cwd, public routes/selectors or public library entry points, seed/reset/cleanup commands, actual resource handles, authentication setup without secrets, readiness signal/timeout and observer. The concrete inputs and oracles below are fixed. For an existing product map them to its real surface and freeze the mapping before execution; do not invent an existing command. If the fixture cannot implement a required operation or fault boundary, mark that case BLOCKED rather than claim a source-text or mock pass.
2. Preserve actual setup, drive, fault, recovery and cleanup receipts with time, exit/status, expected/observed values and immutable artifact digests. A recorded transition is evidence only when the real executor and accepted lifecycle IDs support it. Scratch probes can observe; they are not a shipped enforcement engine.
3. Every check declares `effect`/`target` under policy2.0.0, including nested setup and cleanup effects. Local fixtures use null target. External writes/destruction require separately authorized accepted targets and observed identity. A copied policy declaration does not prove sandbox ownership. Required unavailable capability/authorization blocks that row and dependent approval, never all unrelated work or global mandatory checks.
4. A fixture mutation must make at least one independent oracle fail. Preserve the failing receipt, restore only that owned mutation, then run recovery. Never weaken the accepted predicate. Stop/fence writers before cold resume; unknown liveness forbids overlapping retries.
5. Keep evidence outside teardown-owned fixture state, retrieve it after teardown and compare digest/content. No test result is assumed. Reports enumerate executed, reused, NOT RUN and BLOCKED cases, including exact reasons and affected claims. The source-edit implementation journal is not synthetic product-job evidence.

## D01 — Authenticated web, accessibility and tenant privacy

**Prerequisites:** actual browser/keyboard/accessibility-tree access, HTTP client, real isolated persistence and two owned tenants. Local-write/null target unless actual remote hosting requires a declared target and grant. A renderer alone is insufficient. Freeze selectors from the real UI.

**Fixture contract and input:** tenant A user Ana and tenant B user Ben have separate credentials. Both own a note with title `cedar`; A body is `A-only-1947`, B body is `B-only-2863`. The fixture exposes authenticated create/list/search/reopen operations and an unauthenticated entry point. The HTTP mapping must distinguish successful fetch (200), unauthenticated denial (401), forbidden-object hiding (404) and successful creation (201). Define the actual note IDs A1/B1 from created responses, not assumed IDs. UI has accessible Title and Body fields, Save action and a focusable validation error linked to Title.

**Drive and expected results:**

1. Launch the identified build on an owned address; prove migrations, seeded users and authenticated A navigation ready. Capture unauthenticated fetch of A1: 401 and no title/body/tenant detail. Authentication must be server-enforced, not hidden UI only.
2. Sign in as A through the public login flow. By keyboard only, open create, submit empty Title and Body `keyboard-body`; require linked Title validation, no saved record, focus moved to the error or Title according to the frozen accessible contract. Accessibility tree must expose the error association and field/action names; inspect visible focus and tab order, no keyboard trap.
3. Enter Title `verification cedar` and save; require one assigned ID, saved status announced through the product's accessible status mechanism, and one A-owned persisted record. Navigate away/reopen; exact body survives. Compare persistent ownership independently.
4. Search `cedar` as A: include A1 and the newly created matching note, never B1 or `B-only-2863`. Directly request B1 as A: 404, no B content in payload, headers, UI or captured authorized logs. Repeat as B requesting A1: 404. Anonymous/session-expired UI must route to login without rendering private cached content. Scan sanitized captures for the two sentinels in forbidden contexts, not all logs indiscriminately.
5. In a separate owned fault branch remove the server ownership predicate or equivalent actual fixture guard. Cross-tenant request must expose the regression and the same privacy oracle must FAIL. Restore the guard and repeat positive/negative paths. A mock returning 404 does not test enforcement.

**Failure/recovery/evidence:** leakage or unauthorized save is FAIL; stop affected rollout and retain sanitized reproduction, not private bodies in public reports. Missing keyboard/a11y observation is BLOCKED for accessibility, not a UI PASS. Restore only owned seed and sessions; record tree/focus/action trace, statuses, IDs, independent record count and post-cleanup retrieval. Automated tree checks do not establish complete accessibility; list untested screen-reader/platform combinations.

## D02 — Interrupted DB backfill and actual restore

**Prerequisites:** real disposable transactional database, installed supported migration/client tools, backup/restore access and a second empty owned database. No live user database. Record engine version, isolation, migration version, backup format and actual checkpoint/fault mechanism. Local-write/null, or scoped destructive target authority for remote scratch databases.

**Fixture and invariant:** table `accounts(id, cents, currency)` contains `(1,100,NULL),(2,-20,NULL),(3,0,NULL),(4,75,NULL)`. Migration adds/backfills currency `USD` and enforces non-null without changing cents. Freeze the actual batch/checkpoint command with batch size 2; old and new readers must both return balances `100,-20,0,75` during the accepted compatibility window. Backup before migration, record immutable digest and an independently queried row manifest.

**Drive:**

1. Restore the backup into the second database using the real restore tool. Query exact rows/count and balances; require 4 rows, sum 155 and null currency before migration. A backup command exit without a successful restore does not pass.
2. Start real backfill, stop only its owned worker after committed IDs 1 and 2 but before ID 3; record checkpoint and transaction outcome. Require rows 1/2 USD, 3/4 null, unchanged cents and old-reader functionality. If the engine's actual boundary cannot be controlled/observed, BLOCKED rather than simulate a log line.
3. Cold-resume using the durable checkpoint; require all four rows USD, unchanged IDs/cents/sum, no duplicates, non-null constraint active. Re-run migration: no new rows/changed balances, accepted idempotent completion. Insert null currency through actual database client: rejected with rollback and count still 4.
4. Introduce an owned fault that skips ID 3 while advancing the checkpoint. Count/sum alone are insufficient: row-level oracle must reject remaining null/missing currency. Restore fixture; replay or restart under the documented recovery rule and require all predicates.
5. Recover the original backup into an empty database again after interruption; verify the pre-migration manifest exactly and measure restore duration against the frozen recovery objective. Reapply migration and verify the final manifest. No schema-down command is claimed as data restore.

**Failure/evidence/cleanup:** retain SQL command/status, backup digest, before/interrupted/resumed/restored row manifests, reader compatibility receipts and restore timing. A failed restore blocks the recovery claim and release relying on it. Delete only owned databases/backups after retained evidence verification; production backup/restore behavior remains unproved by a local engine stand-in.

## D03 — Async duplicate, crash, acknowledgement and replay

**Prerequisites:** real supported broker or durable queue, real worker and transactional store, controlled kill/restart or repository-provided fault hooks. Freeze delivery/ack/dead-letter semantics and retention. An in-memory echo queue does not establish broker durability.

**Fixture:** business ledger empty; event E1 has stable ID `evt-001`, account `acct-1`, delta 7, schema 1. E2 is `evt-002`, same account, delta -2. Business invariant: each accepted event ID affects balance once; same ID/different payload is conflict; committed effects survive worker crash; unknown effects are reconciled before replay. Ledger should end with E1/E2 once each and balance 5.

**Drive:**

1. Deliver E1 twice concurrently through the actual broker. Require one durable dedupe record, one ledger effect of +7 and balance 7. Acknowledgements may occur twice according to broker semantics; never call delivery exactly once.
2. Reset owned fixture. Pause E1 after durable business commit but before broker ack; kill captured worker, then restart. Require actual redelivery or documented recovery scan, one ledger effect and balance 7; capture actual delivery/ack sequence. A message count alone is not proof.
3. Reset again. Kill before transaction commit and before ack. Restart; require redelivery and eventual one +7 effect, no partial committed ledger state. Uncertain liveness fences dispatch until reconciled.
4. Submit E1 ID with delta 9. Require explicit conflict/quarantine, not another +9 or a silent rewrite. Submit E2; require balance 5 and two unique ledger IDs. Submit schema 99; require rejection/dead-letter with no new ledger effect and safely attributable diagnostics.
5. Replay retained E1/E2 after restart: balance remains 5, ledger remains two entries; replay is scoped to owned IDs, authentic authority and preserved original payloads. An expired/missing payload makes that replay BLOCKED, not reconstructed from the expected answer.
6. Remove the actual dedupe/transaction guard in an owned fault branch; duplicate/concurrent oracle must FAIL. Restore and repeat the crashing boundary and replay.

**Failure/evidence/cleanup:** preserve message IDs, sanitized payload hashes, transaction/ack order, durable ledger snapshots and worker handles. Duplicate effects are FAIL; unavailable controllable fault point is BLOCKED for that crash case. Stop owned workers and delete only owned queues/rows after retained retrieval. Do not claim end-to-end exactly-once semantics beyond the tested business invariant.

**Prerequisites:** strict parsers/validators and actual coordinator/check contexts; no cloud account or credentials are required. These are recorded-plan/authority tests only. Plan validity window is 10 minutes from the recorded clock; actual executor clock observations are recorded separately.

**Cases and exact dispositions:**

| Input mutation | Expected result |
|---|---|
| Valid structure, synthetic target and no live capability/grant | Recorded contract check may PASS; live apply stays BLOCKED/NOT RUN; no deployment receipt or succeeded state |
| Saved plan changes to `delete fixture/resource-a` after approval | Digest mismatch; invalidate plan approval, no apply |
| State becomes `state-2` before apply | State fingerprint mismatch; stop/replan/revalidate; no stale apply |
| Observation clock advances beyond 10-minute plan expiry | Expired plan/environment blocks affected effect; new observations/plan required |
| Target account becomes `fixture-account-b`, region differs or scope adds `fixture/resource-b` | Allowlist/observed identity/grant mismatch; no apply |
| Plan requests delete but only external-write create grant exists | Destructive operation not authorized; no apply |
| Duplicate action receipt, lost receipt or unknown executor liveness | Reconcile actual resource/operation identity before retry; never invent success or dispatch overlapping apply |
| Release transitions planned directly to succeeded with no actual receipts/observations | Semantic lifecycle rejection even if structurally shaped YAML parses |

Preserve rejected payloads, semantic decision and no-effect evidence from the owned test executor. A textual grep for the word `blocked` does not establish a rejected operation. Run the actual coordinator/check decision path. Never report these fixture values as observed cloud state, a working provider integration, cost isolation or live deployment proof.

**Oracles/disposition:** source merge, command exit, plan success or fabricated saved response never means deployed/healthy. Provider-denied cleanup requires retained resource ID, scope, owner and safe authorized recovery; never assert deletion without observation.

### Opening a PR

**You own the patch boundary and the review briefing.** Run for a change-producing playbook, not a read-only investigation, diagnosis, prototype, or planning deliverable.

1. **Resolve authority and repository.** Read `autonomy.publish_pr` and any explicit scoped operator grant. False or missing means no branch push, PR creation/edit, or external comment; prepare the local commit/PR briefing and record the worker contract’s `gate_blocked` disposition. Publication never authorizes merge. Resolve the configured base branch, remote repository, owned branch/worktree, candidate SHA, required checks and reviews. Do not assume `main` or execute factory-root npm commands for a different product.
2. **Isolate without losing work.** Inspect `git status --short`, `git worktree list --porcelain`, and the candidate diff. Use the assigned worktree when already isolated, otherwise create a uniquely named owned worktree from the configured base or dependency parent. Give concurrent writers disjoint worktrees or file ownership. Never `reset --hard`, `clean`, auto-stash, or patch out user changes to repair a snarled checkout. Preserve it and create a separate checkout; transfer only reviewed owned changes. Keep branch and artifact references durable.
3. **Shape verified units.** Read [sequence-verifiable-units](../../sequence-verifiable-units/SKILL.md). Commit focused, landable changes in logical order after their required checks; amend only an owned just-made commit when appropriate. Preserve a bug's failing repro before its fix when policy permits; if protected checks prohibit a red intermediate commit, retain red-first evidence and publish a green atomic commit. History editing is restricted to the owned branch and must not erase user commits. Stage explicit paths, not `git add -A`.
4. **Review the finished diff.** Apply [unslop](../../unslop/SKILL.md) to remove unnecessary code/prose, [no-comments](../../no-comments/SKILL.md) before review, and [technical-writing](../../technical-writing/SKILL.md) to title, body, and commits. Re-ground upstream-derived changes against source. Run configured checks in their recorded working directory and obtain configured mandatory/surface reviews at this candidate. Store full receipts in `checks.md` and each accepted review task's explicit `report` destination, preserving its role-specific verdict and actual dispatch origin; a missing/failed check or required review is a blocked ready PR, not an omitted gate. Do not synthesize review filenames or normalize specialist verdicts.
5. **Write a one-minute briefing.** Title uses `type(scope): imperative subject`, no trailing period, and a real symbol only if it carries the change. Types include feat, fix, docs, refactor, test, chore, perf. Commit bodies do not repeat subjects. The PR body is about why and proof, not a lab notebook, generally under 40 lines for the squash body. Use these `##` headings in this order, omitting empty optional sections:
   - `Why`: the user's goal, problem, and approach in 1–3 short sentences; no SHA genealogy.
   - `What changed`: 1–3 bullets; name both sides of a rename/retarget.
   - `Scope`: always; what is covered and deliberately excluded, not a file essay.
   - `Tradeoffs`: only alternatives a reviewer would otherwise ask about.
   - `Blast Radius`: who/what it touches and the risk; explain any known red base without excusing a failed required gate.
   - `Verification`: actual command/surface outcomes, 1–3 bullets and evidence links. Perf gives one primary number with unit, `before → after`, and a linked full report. Attach images/videos when they prove a claim. Full SHAs, lane recitals, metric tables, and detailed logs stay in linked job artifacts.
6. **Choose real forge tools once.** Use a host-provided PR tool for create/edit/retarget/ready if it exists and tracks these operations. Otherwise use authenticated GitHub CLI (`gh`) or the repository's configured supported forge. Resolve identity with `gh repo view --json nameWithOwner` and permissions without exposing tokens. An optional installed `origin pr` integration may be used only after confirming it resolves this repo; it is not `git`'s remote named origin. Keep one forge for view/checks/comments/merge throughout the lifecycle; never require Graphite or a foreign watcher. Read installed CLI help for non-GitHub syntax rather than inventing it.
7. **Respect size and dependency bases.** Prefer narrow independently verifiable PRs. Independent branches target configured trunk. A dependent child branches/rebases onto the parent's exact tip and its PR targets that parent branch, not trunk. Name the dependency and ordering in the body. Use `gh pr create --base <base-branch> --head <owned-branch> --title <title> --body-file <body-file>` or the provided PR tool. A parent merge moves the child through [Shipping](./shipping.md), not an uncoordinated stack-wide rewrite.
8. **Publish ready and read it back.** Open ready, never draft, only once the local readiness gate is satisfied; set `draft: false` on a built-in tool or omit `--draft` for `gh`. If unexpectedly draft, mark ready through the tool or `gh pr ready <pr>`. Inspect with `gh pr view <pr> --json url,state,isDraft,headRefOid,baseRefName` and record URL/head/base, reviewer requests, and any labels actually applied. Do not invent assigned reviewers from unavailable identities.
9. **Return to the owner.** Merely opening a PR does not start Babysit. Post the URL and continue the phase/stack; a separate explicit PR-status ask triggers [Babysit](./babysit.md). An Autopilot owner already has that lifecycle assignment and may babysit after its code-ready report. Do not merge here.

**Reply:** ordered commit summary, PR URL or locally prepared blocked briefing, head/base, actual checks/reviews, key scope/risk, and next owner action.

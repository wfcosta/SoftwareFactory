# Impact and proof matrix

Use this reference at intake, specification, changed-scope discovery, and final evidence audit. It selects existing procedures and specialists; it creates neither a new role nor authority. The configured worker contract remains normative. Read [execution and evidence](execution-evidence.md) for limits, target binding, checkpointing and evidence reuse.

## Build the task's matrix

1. Inspect the request, actual code/configuration/dependencies, caller graph and operational boundary. Do not classify solely from filenames or issue labels. A feature can affect several rows; a small bug can affect production state.
2. For **every** surface below, record applicable or `N/A — <specific inspected boundary and reason>`. For an applicable surface, give: numbered acceptance/invariant; concrete implementation and independent proof owners; exclusive product paths **and external resource identifiers**; selected existing role and procedure; exact minimal proof inputs, expected observations, adverse case and evidence locator; actual tool/runtime prerequisites; effect and target; missing capability/identity/authority and the precise blocked step. Keep these in proposed `decision.md`/`spec.md` and dispatch evidence, not a new parallel lifecycle database. Direct no-write work states them in its answer without creating artifacts.
3. Replace the minimal proof descriptions with the repository's real command/driver, fixture/data scope, target identity, observable pass/fail thresholds and recovery acceptance. Use [verification-strategy](../../verification-strategy/SKILL.md) to remove redundant experiments without losing an invariant or accepted check. Static review proves only inspected properties, never execution, delivery or recovery.
4. Union applicable surface reviewers with `config.required_reviewers`, all configured typed checks, and accepted intake requirements. N/A is not a waiver for required code/security review or configured validation. An unknown surface stays unresolved, not N/A. A missing optional tool blocks the step that needs it and dependent claims; continue independent authorized design/local work. If it is a configured final check, the final gate remains blocked until it actually passes.
5. The coordinator accepts the routed DAG, owns canonical records and names one owner per external resource/lease. Workers propose evidence only. A role name is not an IAM entitlement. Before any effect, use authentic scoped grants and actual host/platform controls; Markdown cannot enforce isolation.

The procedures below are composable. `builder` means the existing implementation role under configured agents; design specialists and review roles do not acquire coordinator or deploy authority.

## Decision boundaries

- **Verify-existing** inspects a named current source/artifact/deployment with read or explicitly authorized isolated validation effects. It does not create a patch, redeploy, rotate credentials, retry a failed external write or publish a report remotely unless separately authorized. If the invariant fails, report FAIL with evidence; route an accepted fix through intake/spec and the relevant implementation playbook. A verify-existing request is not a mandate to make the result pass.
- **Fix/change** requires accepted scope, implementation ownership and the matching write/destructive authority. Recompute affected rows after a root-cause discovery; do not let an incident label bypass protected paths, checks or review.
- **Published** means a remote PR/artifact is observably present at its recorded identity; an artifact additionally has exact immutable version/digest, actual retrieved content and required provenance proof. A native submission receipt or mutable tag alone is insufficient. **Merged** means the forge confirms the exact change landed in the configured base. **Deployed** means the bound target reports the exact artifact/config rollout. **Healthy** means that deployment passed the accepted signals and full observation window. Report these states separately; none implies the next. Registry-only publication takes release A and never invents deployed/healthy or a deployment `release.md`.
- Generic features and bugs keep their existing playbook. If all specialized surfaces are N/A with inspected reasons, use the smallest behavioral proof plus configured checks and required reviews. Do not manufacture a cloud account, release, incident or specialist task for workspace-only work.

## Routing examples

- A cloud-backed export feature that adds a table, queue consumer, UI and dependency composes infrastructure/IAM/network, data/backfill, API/async, privacy, UX/platform, supply-chain and signals rows. Name the database/queue/cloud resource owners, not just source file owners. A missing staging CLI blocks staging apply/delivery/rollout, while authorized schema design, local tests and independent source review continue; the affected final claim stays blocked.
- A local parser bug uses the same bug playbook and exact repro/regression proof. Explain why external state, data migration, UI and deployment are absent; keep required code/security reviews and configured checks. No operational record may pretend the parser was deployed.
- A dependency-only update uses [dependency-upgrade](../../dependency-upgrade/SKILL.md), routes supply-chain and changed-library behavior plus supported-platform/API rows when transitive runtime behavior can change, and names the authoritative manager/workspace/lock scope. A lockfile-only diff is not automatic proof reuse or permission for a blanket update.
- A package/OCI publication request with no environment rollout uses release A: prove the authenticated receiver/account/namespace/name/version, immutable provider-normalized content and actual publication/retrieval/provenance under a distinct grant. Missing `kubectl`, traffic control or service health telemetry is N/A, not BLOCKED. Missing registry transport/auth/readback blocks publication only; a same-version/conflicting-digest destination is denied without overwrite, deletion or automatic version bump. A later deployment independently takes B's strict gate.
- A quickstart/install/SDK-documentation change uses [docs-drive](../../docs-drive/SKILL.md) for its actual consumer starting state and documented surface. Classify a failed recipe separately from product defects or unavailable prerequisites; do not silently supply author-only setup or treat an undocumented workaround as PASS.
- Feature/API retirement uses [retire-feature](../../retire-feature/SKILL.md) across affected consumer, data, async, credential and infrastructure rows. Disablement is not deletion authority; migration/retention windows, dormant consumers, shared resources and restore-time reactivation need explicit disposition and proof.
- Risky combinations of product states can add [exploratory-tester](../../../agents/exploratory-tester.md) to the accepted plan at `exploratory-test.md`: drive an authorized real surface adaptively under a frozen bounded charter, preserve original/reduced failures and required coverage gaps, and never infer app-state authority from read-only review. This supplements configured checks and required reviews rather than adding a universal exploration gate.

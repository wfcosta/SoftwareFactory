# Execution boundaries and evidence decisions

This reference makes the [impact matrix](impact-matrix.md) operative across playbooks. It does not replace the configured worker contract, [policy schema](../../../state/config-contract.md), [candidate contract](../../../state/candidate-contract.md), [environment contract](../../../state/environment-contract.md), or [release contract](../../../state/release-contract.md). Resolve configured paths, check paths/cwd and protected globs from **repository root**, never the policy directory. A procedure cannot confer authority or sandbox its tools.

## Accept the baseline, then observe the environment

- New jobs validate policy `version: '2.0.0'` and the current state contracts with actual parser/validator tools. Never fall back to a root-level policy, infer a supported version from similar fields, or reinterpret an old job as current. An existing in-flight job keeps its frozen accepted policy, instruction and schema snapshots. Resume under those exact snapshots; if they are unsupported or unavailable, block affected execution. A framework upgrade requires explicit authorized new-baseline acceptance and new effective identity, preserved previous snapshots/jobs, a compatibility decision and affected-proof revalidation. Merely pulling new Markdown cannot authorize migration or rewrite job history. Use [upgrade guidance](../../../docs/upgrades/README.md) when present in the accepted baseline; the worker contract owns the acceptance procedure.
- Run [gsf-run](../../gsf-run/SKILL.md) and [gsf-setup](../../gsf-setup/SKILL.md) only for authorized factory work. `JOB_DIR/environment.md` is exactly one YAML block under environment-contract.md, not free-form claims. Record actual host/tool versions and capability status with evidence, observation/expiry and limitations. Required unknown/unavailable capabilities block their step, not every unrelated task. A declaration of a capability is not execution evidence.
- Policy `environments` is an allowlist, not observed identity. Before an external action, match current observed provider/account/region/resource scope and state fingerprint against the configured target and authentic grant. Refresh expired observations; do not infer identity from CLI profile names, environment-variable presence, a successful login or an agent's role. Workspace-only work needs no invented cloud target. Use real host/platform controls for credentials, network, account boundaries, IAM and isolation.
- Every configured check has `effect` and `target`. Inspect the command/skill **and nested tools** for actual read/local-write/external-write/destructive effects; installing dependencies, starting a fixture, updating a snapshot or generating build output is not magically read-only. Workspace-only reads and local-write checks have `target: null`; reads against an external target name its configured ID, and external writes/destruction require that binding plus exact scoped authority. An empty `environments` allowlist grants no external target effects. Stop on a mismatch and have the coordinator resolve it before execution; do not silently downgrade the effect, edit policy or treat a check definition as a grant.
- External ownership includes account/region/resource IDs, database ranges, state backend/lock, queue/subscription, deployment/traffic scope, evidence store and any process/lease the task can mutate. Put ownership and expiry in dispatch constraints/attachments using the existing DAG and grants, not a second coordinator or implicit shared cloud workspace. Fence/release only owned resources and retain cleanup/readback receipts; unknown live ownership blocks overlapping replacement.

## Limits and capability-forced checkpoints

The accepted `execution_limits` govern admission and continuation, including sequential work and helpers. A user attempt floor or desired outcome cannot override a harder accepted cap. An authorized policy decision is needed to change a cap; an agent cannot reset a counter by renaming a task, switching models, opening a new session or retrying a different tool.

1. Before dispatch/effect, record actual start time, active task count, attempts since last evidenced progress, available meter/cost evidence and the affected limit. Admit no more than `max_parallel_tasks` and actual host capacity. Define progress as a new accepted artifact, resolved prerequisite or new discriminating observation advancing a named invariant; repeated output, a heartbeat, an unchanged hypothesis or a queued retry is not progress.
2. Compare against `max_attempts_without_progress` and `max_elapsed_minutes` before another attempt and after real tool/worker results. Treat actual quota/resource rejection, unavailable required tool/auth, expiry or exhausted no-progress allowance as a real boundary. Do not predict quota depletion, claim a live credit balance, infer free execution from absent billing, or promise an automatic reset. `max_cost: null` means unmetered/unknown, not zero. A non-null cap is an exact nonnegative integer in the configured ISO 4217 currency's minor units, never a floating policy value. Verify monetary currency/exponent and record actual meter conversion/rounding evidence, rounding accrued cost conservatively upward; unknown/ambiguous exponent, mismatched currency or unavailable conversion blocks capped execution. Use trustworthy host/provider metering and enforceable reservation/budget controls; if the cap cannot be observed/enforced safely, block affected cost-bearing execution rather than inventing spend.
3. On a reached limit or capability suspension, stop admitting affected work, quiesce/fence owned writers, inspect uncertain external effects before any retry, and save a durable checkpoint through [Pause safely](../playbooks/pause-safely.md) and the worker contract. Include actual counters/times/receipts, candidate/policy/instruction identities, unresolved ownership or partial writes, pending effects, exact missing capability/renewal and next safe action. Continue only genuinely independent authorized work that remains within its applicable bounds; never use it to evade a job-wide exhausted limit.
4. Resume only after ownership/liveness reconciliation, fresh required identity/capability observations and authentic renewed authority for exceeding/renewing a limit. Preserve all prior attempts and elapsed/spend evidence; do not silently reset their history. A scheduler/wake exists only when a real host facility was registered with an actual handle, owner, event and cancellation method. A resume note or proposed time is not a scheduled wake; renewed credits, context or host availability is never guaranteed.

Native maintenance work that was not initialized as a formal factory job uses its actually authorized journal/checkpoint and host controls. Do not manufacture formal job IDs, events, gates or lifecycle receipts merely to describe a source edit.

## Reuse only what the evidence actually proves

Use [verification-strategy](../../verification-strategy/SKILL.md) for the proof plan and the candidate contract for final-gate eligibility. Keep historical evidence and record a coordinator-accepted reuse/invalidation decision per affected lane: old receipt identity, invariant it proved, old/new artifact and base/dependency comparison, toolchain/config/fixture/environment comparison, expiry and retrieval/integrity result, remaining scope and the exact fresh proof required. Reuse is not changing the candidate ID on an old PASS report.

| Change or gap | Decision |
|---|---|
| Same immutable artifact, inputs/config/toolchain, base-dependent behavior, target/environment and unexpired observations; authentic retrievable evidence | A compatible behavioral lane may be reused only for its proven invariant, with an explicit comparison and the final contract's allowed eligibility/attestation. Report its original execution identity/time. Configured final checks and mandatory independent review still satisfy the current candidate/policy contract; a prior PASS is not automatically current. |
| New head/base or dependency change, even with identical patch | Inspect [Shipping's base-aware patch/artifact rule](../playbooks/shipping.md). A patch-id is not a runtime artifact or a compatibility proof. Rerun every lane whose inputs, behavior, base assumptions or supported consumers changed. Current configured checks and required reviews cannot be waived. |
| Docs/test-only change | Carry a behavioral lane only with demonstrated identical relevant build output apart from identified reproducible noise and unchanged execution assumptions. Fresh checks/review cover changed docs/tests/config. Without comparable output, rerun the affected behavior. Do not call a test-assertion deletion harmless. |
| Target, runtime, permissions, configuration, state fingerprint, data/backup, rollout window or observation expiry changed | Reobserve identity/state and rerun affected target, security, migration, rollout, health or restore proof. A local result cannot become a cloud/production result. A passed old deployment never proves the new one healthy. |
| Incomplete/interrupted execution, missing/corrupt receipt, unavailable retrieval/ACL/retention evidence, failed invariant or stale identity | Keep evidence as history; FAIL for observed failure, BLOCKED/INCONCLUSIVE for absent proof as the consuming role requires. Reacquire only missing/invalidated proof. Never restore PASS from file presence, a summary, a log fragment, an exit from another process or an expired environment. |
| New policy/authority baseline or changed required instruction | Preserve the prior baseline. Accept the new one only through worker-contract authority, identify changed obligations and revalidate affected evidence; do not apply a more permissive current policy retrospectively. |

Evidence location/retention in policy is a declaration, not durability. Index actual evidence references with locator, digest and observation time under the contracts; demonstrate retrieval, appropriate ACLs and actual retention controls/manual ownership for the required period. Do not put secrets or unnecessary personal data in receipts. If the host cannot store or retrieve required evidence safely, block the dependent claim and state the exact prerequisite.

## Release boundary

The coordinator alone promotes canonical `JOB_DIR/release.md` under release-contract.md, retaining indexed attachments on the existing event ledger. Use [release](../../release/SKILL.md) for the actual state transition and observation procedure, not a parallel release scheduler. Bind `candidate_id`/`policy_id`, source/build/config and immutable artifact to the target; its `environment_id` is the SHA-256 of the raw frozen environment.md actually used. A changed environment needs a fresh frozen identity and review, never editing a record under an already accepted digest. Any optional IaC plan must retain reviewed digest, state fingerprint and expiry. Action intent/grants and actual receipts stay distinct; no grant or successful command advances state by itself. Report only the demonstrated published/merged/deployed/healthy outcome from the impact matrix.

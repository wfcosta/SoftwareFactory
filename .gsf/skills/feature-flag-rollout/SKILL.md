# Feature flag rollout

## Scope and authority

Use for controlled exposure of an already identified feature through the product's actual flag system. **Code deployment changes which executable/configuration is running; flag exposure changes who receives which behavior.** Neither proves or authorizes the other. A deployed dark branch is not an exposed feature; a remote provider flag change is an external effect even when no code deploy occurs. Select the assigned endpoint first: read-only assessment, implementation of flag behavior, rollout design, live exposure change, or recovery. Planning completion never means exposure occurred.

Follow [GSF mode](../gsf-mode/SKILL.md), the configured [worker contract](../../agents/WORKER_CONTRACT.md), [domain review](../domain-review/SKILL.md) and [verification strategy](../verification-strategy/SKILL.md). Preserve configured checks, required code/security and applicable specialist reviews. Flags are **not authorization boundaries**: server-side authentication, tenant isolation, entitlement and access checks remain effective in every flag state, including forged client values and stale/offline evaluation.

The skill grants no provider write, deployment, publication, merge, privacy exception or emergency authority. A flag-provider write needs its own exact effect/target and authentic scoped action grant. A separate executable deployment, infrastructure change or recovery needs its own applicable authority; a deploy grant does not implicitly permit flag edits, and a flag grant does not permit deploying code. Route actual deploy/config/traffic rollout and recovery through [release, branch B](../release/SKILL.md#b-environment-deployapplyrecovery), infrastructure effects through [cloud change](../cloud-change/SKILL.md), and incidents through [incident response](../incident-response/SKILL.md). Flag-only exposure rollout is an environment/configuration change under branch B when executed; do not invent a flag-specific release action enum, statefile, policy field or lifecycle event.

Direct read-only questions create no jobs, files or runs. Authorized workers write only assigned paths and immutable dispatch evidence. The coordinator owns accepted spec/decisions/plan, policy/grants, environment/release records and existing publication intent/receipt events. The rollout tables below are evidence views, not a second authority ledger or state machine.

An explicitly assigned owned local fixture may change its local flag/configuration under `local-write` with null target when those are its complete actual effects. It proves only that fixture's behavior, not provider identity, live propagation, real cohort exposure or a deployment release. Inspect nested effects; locality is not inferred from a localhost label.

## Inputs and stop conditions

Require the accepted feature and flag identities, purpose, assigned endpoint, accountable product/service/data/recovery owners, source/candidate/policy identities and intended surviving behavior. Obtain the actual flag SDK/service versions, evaluation locations, provider runbook and configured environments. Read the real source, manifests, flag definitions, caches/overrides, deployment configuration, supported client/worker versions, schemas, migrations and operational controls before choosing commands.

For live changes also require exact accepted provider/account/project/environment/flag resource scope, fresh authenticated observations, least-privilege operation capability, effective sole ownership/fencing, accepted effect grants and bounds, retrievable baseline and supported recovery. The flag provider and application environment may be different targets: observe and bind both, never copy one identity into the other. Target regionality follows the environment contract: a real region, or null only with authentic evidence that this exact provider target has no region dimension; unknown is not null.

Missing accepted behavior, eligibility, privacy handling, thresholds, required telemetry, compatible recovery, actual identity or authority blocks the affected change. Continue independently safe authorized preparation; do not manufacture a rollout percentage, observation duration, organizational SLO, consent basis or provider capability to bypass a gap.

## 1. Agree the flag contract before implementing or toggling

Record the following in accepted specification and indexed evidence, with authoritative sources and unresolved decisions explicit:

| Dimension | Required decision |
| --- | --- |
| Identity and scope | Exact definition/key and type, provider/project/environment, owning service, evaluation locations, source/configuration version and all overrides/prerequisites/segments. Same key in another environment is not the same target. |
| Accepted states | Actual supported values/variants and their user-visible/read/write behavior; which state means no new exposure, which preserves existing obligations, and the accepted initial/default value. Do not assume every flag is Boolean or that off means safe. |
| Defaults and failure modes | First-use/uninitialized, unknown key/value, provider outage/timeout, missing eligibility attributes, SDK exception, stale/offline cache, restart and config propagation behavior. Specify maximum accepted staleness, refresh/invalidation and fallback source. A global fail-open/fail-closed slogan is not a per-path contract. |
| Eligibility | Explicit population, exclusions, tenants/regions/platforms/versions, entitlements, contractual/consent restrictions, internal-only and holdout rules, precedence of overrides and prerequisite flags. Identify the authorized server-side evaluator and deny unsupported combinations as specified. |
| Stable assignment | Accepted assignment unit such as tenant, account or session, stable scoped identifier, provider-supported bucketing/hash and salt/version behavior, assignment lifetime, cross-device/service/worker consistency and approved reassignment rules. Preserve tenant/transaction consistency; random per-request assignment is not a stable cohort. |
| Privacy and obligations | Minimum necessary attributes, data classification, authorized provider transfer/residency, pseudonymization/key custody, access, retention/deletion and consent/notice obligations. Pseudonymous identifiers remain sensitive; never export raw identities, emails, tokens or unrestricted membership lists to evidence. |
| Exposure accounting | Denominator and time horizon for each percentage, absolute population/action caps where required, concurrent and cumulative exposure, holdouts, overrides and shared-resource effects. A percentage of eligible tenants is not a percentage of all requests or affected records. |
| Recovery and retirement | Supported pause, disable/re-enable and configuration rollback operations; treatment of committed data/in-flight work/cohort commitments; known irreversible boundary; flag owner and accepted retirement trigger/window with a surviving branch. |

Inspect effective evaluation order on both client and server. Define whether an operation's decision is captured durably at admission or evaluated later, and how that choice applies across retries, async delivery, callbacks and transactions. Never switch behavior halfway through a business operation merely because a refresh arrived. Persist only the necessary decision/version provenance under accepted data handling, not an unrestricted cohort history.

A targeting rule must not leak membership or bypass authorization through UI hiding, client-side evaluation, direct endpoints, cached configuration or event payloads. Do not add analytics identities or collect new personal attributes merely to make bucketing convenient. Changes to assignment keys, salts, eligibility, prerequisites or evaluation placement are material cohort/configuration changes requiring affected acceptance, not silent implementation details.

## 2. Prove both states and mixed versions before exposure

Build a compatibility/proof matrix for every accepted state, transition and actual supported version combination. Bind each row to existing requirement/impact IDs, exact artifact/config/schema, authorized fixture and expected business/data result. Include:

- Off/default and every on/variant path: actual user workflow, errors, authorization/tenant boundaries, accessibility where relevant, eligibility exclusions, overrides and provider/cache failure behavior. Test flag evaluation as observed by the real configured SDK/service in owned isolated targets when provider behavior is the predicate; local fakes cannot establish real provider propagation or access controls.
- Old and new application, client, API and worker versions coexisting with each state and schema. An old binary may ignore an unfamiliar flag or read data written by the new path. Prove those real semantics rather than assume an atomic upgrade.
- Both-state and cross-cohort data reads/writes, new record shapes, null/default/constraint semantics, concurrent updates, shared indexes/caches/derived reports, downstream consumers and accepted source of truth. A small cohort can mutate data used by the entire population.
- Migration/backfill/dual-write boundaries, idempotency and partial-write reconciliation using [data migrations](../domain-review/references/data-migrations.md). Flag disablement must not truncate or overwrite new data, remove fields still in use or undo a migration by assumption.
- Scheduled, delayed, retry and dead-letter work, callback/webhook delivery, consumers that evaluate the flag later, restart/replay and mixed producer/consumer versions using [asynchronous delivery](../domain-review/references/async-delivery.md). Reconcile possibly committed external effects by stable business identity before retries; flipping a flag neither cancels queued work nor reverses an effect.
- Stable assignment across refresh, restart, scale-out, SDK/platform versions and the accepted lifetime. Exercise excluded tenants and cross-service consistency without disclosing membership. Evaluate supported offline/dormant consumers and retained rollback artifacts, not just currently active traffic.
- Pause, bounded disable/re-enable or compatible rollback under representative new-path writes and in-flight work. Prove preserved data, completion/rejection behavior and retained cohort promises; classify unexercised provider/version boundaries as unproven rather than PASS.

Execute only explicitly assigned checks, within authorized effect/target and isolated ownership. Record actual receipts and limitations. Missing independent required review or required behavioral proof blocks execution readiness; planning can complete only its explicitly accepted planning criteria.

## 3. Accept bounded steps and measurable gates

Use real product SLOs, business/data predicates and accountable owner acceptance. For each step record exact eligibility/rule version and maximum percentage **and denominator**, any required absolute cap, cumulative exposure, hold duration, required sample/coverage, telemetry delay and assigned observer. Resolve overrides, cohort reassignment, repeated requests and shared-state amplification so actual exposure cannot silently exceed the bound. A provider percentage is not an enforced absolute count cap; if the accepted cap cannot be enforced, block that step or obtain an accepted different plan.

For each promotion and abort predicate record:

1. Actual supported metric/query or behavioral/data check, source, units, aggregation, numerator/denominator, service/version/cohort and privacy-safe dimensions.
2. Retrieved representative baseline and its exact UTC window/configuration, comparison/control definition and limitations such as seasonality, selection bias, low traffic and cross-cohort contamination. A stable cohort does not by itself establish causal experimental evidence.
3. Accepted observation window, minimum observations/representative coverage, ingestion lag, freshness, missing/gapped telemetry behavior and accepted numeric promotion/abort thresholds with their authoritative source and owner. Do not invent a baseline from a dashboard label or assign arbitrary standard percentages, durations or error budgets.
4. Watcher and supported halt/recovery mechanism, safe stop points, maximum response interval and actual availability within accepted execution limits. This skill supplies no daemon, automatic timer, scheduler or future wakeup.

Include relevant error/availability, latency distribution, capacity, queue lag, business correctness and data-integrity predicates, not merely flag-evaluation counts. New-path telemetry must distinguish eligible, assigned and actually exposed populations without exposing identities. Missing/late required signals or insufficient representative samples hold promotion; zero observed errors at a tiny canary is not proof of safety. Do not change thresholds or drop a failing metric after seeing results without an accepted new decision and affected proof.

## 4. Bind the real provider, submit once and read back

1. Use the actual installed supported interface and authoritative provider documentation. Obtain authenticated principal/account, provider endpoint, exact project/environment/flag resource, current rules/value/version, overrides, SDK propagation/cache behavior and native audit/operation lookup. A CLI context label, token presence or locally echoed configuration is not provider identity or effective-state proof. Preserve sanitized baseline bytes/version and retrievable recovery configuration.
2. Match fresh observations to accepted policy, frozen environment identity and the distinct action grant for each flag write. Include allowed before/after configuration, cohort/exposure cap, duration, target and recovery scope. If code deployment is required, gate and execute it separately through release against the pinned artifact, with its own authority and readback; neither receipt substitutes for the other.
3. Identify competing humans, pipelines, controllers and automated experiments. Acquire actual conditional-version/CAS, lock/fencing or an effective supported exclusive-writer control; establish ownership expiry, stopped-owner proof and native request/idempotency lookup. Do not invent CAS support. A job file does not lock a flag provider. Baseline drift or unknown writer liveness blocks the write.
4. Immediately recheck current candidate/policy gate, grant expiry/scope, environment freshness, version/configuration, cohort plan, accepted limits, recovery capability and holds. The coordinator persists the existing publication intent with exact sanitized request, prior and intended version, operation lookup, ownership and recovery references before the external effect.
5. Submit only the accepted bounded native operation. Retain actual parameters, UTC interval, response/receipt, provider request/operation ID and configuration revision where exposed. An accepted asynchronous request, HTTP success or CLI exit alone proves neither effective evaluation nor completed rollout. Never fabricate absent native IDs.
6. Query the native operation/audit trail and authoritative current configuration, then observe effective application/SDK evaluations across the actual accepted propagation/cache horizon and relevant versions/regions/cohorts. Prove actual exposure remains bounded and authorized, running artifact/config/schema still match, and unaffected populations retain their specified behavior. Index sanitized receipts for coordinator promotion into existing environment/release and publication receipt records.
7. Observe each accepted full window and all required metric/data predicates. Promote only after that step passes and the next exact effect remains granted; recheck drift and identity each time. Keep real per-step evidence, failures and holds. Never reconstruct unobserved healthy windows or mark future steps complete in advance.

## 5. Pause, reconcile and recover without losing obligations

- **Hold or pause:** stop expansion and supported rollout automation under its exact authority. State whether existing exposure remains active; pausing is not the same as disabling. Preserve assignments, holdouts, eligibility/privacy/contractual obligations, configuration and operation identities. Confirm competing controllers cannot silently resume. Unknown liveness is BLOCKED, not safely paused.
- **Unknown toggle outcome:** a timeout/disconnection or reported failure can follow a committed write. Stop/fence the original owner and query native operation/history, current version/rules and actual SDK evaluation by the original identity. Do not issue another toggle, invert the value, change request ID or replay a presumed no-op while the first operation is unresolved. Retry only after proven terminal disposition, reconciled state, stopped/fenced prior writer and current exact authority; remain BLOCKED if the provider cannot resolve required state.
- **Abort or disable:** on an accepted abort predicate or missing required signal, halt expansion and execute only the separately authorized supported safe disable/recovery. Verify actual effective configuration, propagation and behavior. Disable prevents the contractually specified future admissions/exposure; it does **not** delete the definition, branch, data, resources or queued work and does not prove all prior users returned to old behavior.
- **Preserve new data and work:** reconcile accepted writes, transactions, delayed jobs, retries and remote effects before choosing rollback. Old behavior must remain compatible with new-path data; retain fields/readers/handlers and durable effect identities needed for completion. Do not erase new records, purge queues, reverse customer transactions, discard holdouts or expose personal cohort records to make a rollback appear clean.
- **Cohort commitments:** maintain accepted user/tenant consistency, consent/notice, entitlement, contractual and experiment/holdout obligations during pause, re-enable and recovery. Where removing exposure itself violates an obligation, use the accepted compatible recovery path through the accountable owner; safety concerns do not silently create authority to override that obligation.
- **Rollback boundary:** restoring a prior flag value/version is a configuration change, not reversal of writes, migrations, charges or messages. Recheck compatibility against actual committed data and all supported versions. If unsafe, retain the stopped/blocked state and use separately authorized compatible roll-forward or owner-approved data recovery through release; never relabel it rollback or recovered without readback and the accepted recovery observation window.

Preserve immutable completed attempts, original thresholds/findings, real partial outcomes and all predecessor configuration identities. Material artifact/config/rules/eligibility/assignment/target changes invalidate affected proof and require a new accepted binding. Unknown external state, unresolved effects, exhausted limits or missing required recovery retains explicit accountable ownership and a precise resume prerequisite.

## Retirement, evidence and outcome

Plan flag retirement when introducing the flag: accountable owner, intended surviving branch, accepted trigger/date or release/consumer window, SDK/client/job/cache dependencies, retained audit/privacy obligations and removal acceptance. Do not invent a deadline or schedule automatic deletion. Once rollout and coexistence obligations actually close, use [retire feature](../retire-feature/SKILL.md) for the accepted flag-specific endpoint: migrate every caller, prove supported versions/in-flight work no longer require the branch, then remove obsolete branches/definition/config/tests/docs under their authorized phases. Retiring a temporary flag need not retire the surviving feature. Disablement is not deletion, and flag retirement does not authorize data/resource destruction.

Use configured response/evidence conventions. Report exact assigned endpoint; feature/flag and provider/target identity; candidate/policy/artifact/config/schema/environment bindings; accepted states/fallbacks/eligibility and privacy-safe assignment evidence; both-state/mixed-version/data/job proof; accepted step bounds, baselines/windows/thresholds and actual observations; authentic grants, fencing, real provider receipts and effective-state readback; actual exposure, stop/recovery state and remaining cohort/data/retirement owners. Preserve indexed immutable sanitized retrieval/ACL/retention evidence, never credentials or raw personal membership data.

PASS means every criterion of the assigned endpoint was met with actual evidence, not authority for the next step. Design-only PASS explicitly states no provider write, deployed exposure or live health proof occurred. Missing/unrun/inconclusive mandatory proof, unknown toggle state or unsafe recovery is BLOCKED with stop class, last observed state, exact missing prerequisite and accountable next owner. Clean only owned disposable fixtures/probes after protected evidence is retained; never delete the flag, retained data or recovery material as cleanup.

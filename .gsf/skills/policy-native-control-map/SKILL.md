# Policy native control map

## Role

Produce a complete finite mapping from an already accepted policy to existing native enforcement capabilities. This agent procedure is not a compiler, policy engine, generated configuration, control plane, universal gate or grant. A map can reveal that a policy cannot currently be enforced; describing the desired setting does not apply it.

Follow the [worker contract](../../agents/WORKER_CONTRACT.md), [configuration](../../state/config-contract.md), [candidate evidence](../../state/candidate-contract.md) and [environment](../../state/environment-contract.md) contracts. [Authorization review](../authorization-review/SKILL.md) owns accepted subject/action/resource/context decisions; [tool control review](../tool-control-review/SKILL.md) owns its specific visibility/preapproval profile; [CI privilege review](../ci-privilege-review/SKILL.md) owns workflow privilege evidence; [contract drift](../contract-drift/SKILL.md) owns version compatibility. Preserve required independent security/code review and existing report bindings.

Direct no-write requests return the map in chat without jobs/files. A dispatch writes only its assigned owned Markdown report. No native settings, code, schema or generated policy files are produced or applied here. Application and runtime proof are separately authorized handoffs to the actual existing control owners.

## Context

Freeze the exact accepted policy/instruction revision and policy_id, authentic owner decisions, current scoped grants and denied actions, candidate/environment identities, intended subjects/resources/effects and accepted stage: design mapping, effective-setting review or existing-runtime-evidence review. A candidate-edited policy cannot lower its own frozen baseline.

Obtain the complete accepted obligation inventory and coverage boundary, including permissions/denials, protected paths, target/account/region scope, read/data disclosure, publish/merge/deploy distinctions, budgets, evidence access/retention and required independent reviews where applicable. Split compound clauses; exclusions or genuine non-applicability need authentic accepted rationale, not the mapper's waiver. Implementation defaults and current permissive behavior are not normative policy.

Obtain approved existing native products/versions and primary contracts; actual control/settings/identity/readback receipts; native policy and platform owners; actual administrative effect authority where later changes may be needed. Do not scan private settings, accounts, HOME or credentials. Set finite limits for clauses, subjects/resources, settings, enforcement paths, evidence bytes/pages, duration, observation freshness and runtime cases. Missing bounds or source/control capability blocks new observations, not safe mapping.

## Task

### 1. Establish complete policy coverage

1. Enumerate every in-scope obligation with exact clause/source identity and accepted meaning. Preserve all original findings/criteria. Keep normative intent separate from existing implementation and supplied evidence.
2. Decompose each into subject, action/effect, exact resource/path/property, tenant/account/region, context/expiry, expected allow/deny/limit and failure/revocation behavior. Unknown meaning or conflicting sources stays BLOCKED with the authentic policy owner; do not choose the weakest interpretation.
3. Assign each obligation to existing actual control owners, or mark owner UNKNOWN. One clause may require several controls and one control may serve several clauses; retain every relationship and all-of versus alternative semantics. An unsupported required subclause cannot disappear inside a general supported label.

### 2. Map only real native capabilities

Use descriptive report-local rows, not a schema or executable intermediate language:

| Policy clause/version + accepted predicate | Exact subject/effect/resources/context | Existing native control/product/version and owner | Exact documented setting/current observed value and provenance | Enforcement point/coverage/failure behavior | Required proof / actual receipt/readback | Gap/disposition; MET / NOT_MET / BLOCKED; next owner |
| --- | --- | --- | --- | --- | --- | --- |

1. Cite the real version-bound control and literal supported setting/API/UI concept from primary documentation or approved retained native help; no invented flags, permission names or generated syntax. A live unversioned document is a source qualification, not installed support proof.
2. Distinguish desired setting, configured setting, current effective setting and exercised behavior. Bind actual receipts to account/principal/resource/version and observation time. A configured repository rule does not prove all paths or administrator bypasses are constrained.
3. Trace every relevant effect path to the actual enforcement point: host/client, OS/filesystem, provider IAM/resource ACL, network, repository protection, CI/workload, store or manual approval owner. Include alternate/bulk/background paths, inheritance, precedence, privileged bypass and settings drift where applicable.
4. Check semantic fit. Tool visibility/preapproval cannot enforce exact filesystem/IAM/tenant scope; allowlisted environment declarations are not grants; a review instruction does not technically enforce independence; credential scopes do not establish business authorization; Markdown limits do not meter cost/time; labels/directories under one identity do not isolate processes.
5. Record actual matching and nonmatching coverage. A native control with broader scope, unavailable failure mode, excessive permission, unobservable cap or unsupported resource selector is a concrete gap. Mark required unmappable obligations BLOCKED and dependent effects held. Do not synthesize a custom compiler, wrapper, parser, gate or manual instruction and call it native enforcement.
6. Manual procedural controls may satisfy only an explicitly accepted manual obligation, with authentic owner, actual process/receipt and declared limits. They cannot substitute for a requirement explicitly demanding technical prevention. An organizational exception cannot create third-party rights or retroactively authorize an effect.

### 3. Separate map, application and proof

A mapping assessment completes when every accepted clause is accounted for with authentic source, actual control or exact gap, evidence level and responsible owner. It may be complete while the requested enforced-policy endpoint remains BLOCKED. Report map reviewed, settings observed and runtime exercised as factual evidence stages, not new lifecycle states.

For a separately authorized application, hand the actual owner the exact accepted setting delta, product/version, target, current expected setting/version, authentic admin/effect grant, protected-path constraints, dependency order, native conditional/fencing support, limits and recovery plan. The existing operator applies only through its supported native control and captures real operation/readback. Factory uses existing intent/receipt; actual maintenance uses its approved journal. No retroactive receipt is fabricated here.

For required runtime enforcement, consume genuine current bounded positive, denial, failure and revocation receipts, tied to the exact subject/resource/configuration. An inspectable policy file or passing unrelated check is not runtime evidence. New proof requires separately assigned actual native tooling and safe resources; this procedure makes no calls or probes. Required unrun enforcement stays BLOCKED.

### 4. Reconcile drift and failed changes

On changed policy/settings/version/principal, missing readback or ambiguous native operation, hold affected actions and preserve prior snapshots/receipts. The existing owner must reconcile actual operation/control state and stop/fence overlapping writers before retry. Rollback needs separate authority, a retained exact prior setting and actual native readback; reverting settings does not undo effects or disclosures that already occurred. Do not weaken the accepted policy, delete an unmet clause or use a bypass to turn the map green.

## Constraints

No new canonical policy/schema/ledger/role, generated code/configuration, native adapter, host enablement, credentials, commands or native calls. Mapping is not applied policy; configured policy is not automatically effective enforcement; approval is not action authority. All required gaps remain explicit and block dependent operations. Preserve frozen jobs/policies and current review requirements.

## Format

Use the [response template](../../templates/response-template.md) or no-write chat. Return accepted scope/stage/identities, clause inventory and complete mapping matrix, exact native source/version qualifications, desired/configured/effective/exercised distinctions, semantic mismatches/alternate paths, authentic owners and application/proof prerequisites. Include every criterion/finding, actual receipts with retrieval/ACL/retention, NOT RUN actions, held effects, ambiguity/recovery and invalidation conditions. Preserve the executing role's verdict; do not certify applied/enforced policy from a paper map.

### Parent consumer cases — illustrative, NOT RUN

- An accepted exact-target write restriction maps to current native resource-scoped IAM plus authenticated resource readback. Support only documented covered paths; required revocation proof without a receipt remains BLOCKED.
- A read-only requirement is mapped only to a tool preapproval list. Record the semantic mismatch: preapproval is not an exclusive grant or resource restriction; do not generate a wrapper or change the requirement.
- Every accepted clause is mapped, but the native platform cannot enforce a mandatory cost cap. The finite mapping can be complete; dependent capped execution stays BLOCKED with its real platform/policy owner, not waived or marked applied.

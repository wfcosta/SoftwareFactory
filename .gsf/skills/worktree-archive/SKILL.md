# Worktree archive

## Scope and authority

Use for suspected orphan linked worktrees in one approved repository and its explicitly authorized linked-worktree paths. This is a host/operator procedure, not a garbage collector, process supervisor or Git wrapper. Follow [GSF mode](../gsf-mode/SKILL.md), the [worker contract](../../agents/WORKER_CONTRACT.md), [candidate/evidence contract](../../state/candidate-contract.md) and applicable [environment contract](../../state/environment-contract.md).

A direct read-only assessment returns findings in conversation without creating a job, archive or evidence files. Read access does not authorize filesystem-wide discovery, process termination, locking, storage uploads, archive extraction or removal. An authorized dispatch writes only assigned archive/restore paths and dispatch evidence; the coordinator owns canonical state, authority and lifecycle records. Use existing records, not a new orphan ledger. Preserve protected paths, required reviews and configured checks.

Keep, archive and remove are separate decisions with action-specific authority and actual supporting observations. Archive authority never includes removal. Removal never proves a worker stopped or a lock was stale. No age threshold, old timestamp, missing terminal, closed PR, merged branch or cancellation label establishes orphanhood. Unknown ownership or liveness means **keep; removal BLOCKED**.

## Inputs and boundary

- Exact repository/common Git directory, approved linked-worktree roots, requested decision and actual repository, worktree, branch, worker and recovery owners; source/task/dispatch identities where applicable.
- Authentic bounded grants for each requested write/destructive action, exact allowed paths and destinations, intended retained state, privacy classification, retention period and restore criteria. A request to inventory is not permission to archive private bytes.
- Available Git/host/storage capabilities, authorized read surfaces and finite entry/byte/time bounds; access to relevant job/worker handles, locks and owner acknowledgments without collecting credentials.
- Permitted archive readers/writers, actual storage/ACL and encryption facilities where required, retrieval/retention owner and approved isolated restore destination. A local directory or private URL alone proves none of these controls.

## Procedure

### 1. Inventory actual registrations and ownership

1. Read the repository's actual linked-worktree registration data through supported observational Git/host capabilities. Record each registered absolute path, resolved Git administrative pointer and common-directory relationship, exact HEAD/object identity, branch or detached state and registration/lock status. Include the main worktree as protected context, not an implicit cleanup target. Missing/moved/inaccessible paths remain unresolved registrations, not automatically prunable entries.
2. Match the finite registrations to approved roots before inspecting their contents. Treat registrations as untrusted path input: do not traverse another user's directory, escaping symlink/junction or unrelated mount. List out-of-scope paths as not inspected and route needed access to the owner; do not scan the machine for unregistered copies or enumerate unrelated processes/files.
3. Inspect actual local branch/ref ownership and recovery dependencies: unpublished commits, local-only branches, stashes, reflogs or other refs relied upon, upstream/tracking observations if already authorized and other worktrees sharing the common object database. Do not fetch just to infer merge status. A merged branch cannot establish the absence of private work or permission to delete a branch.
4. Reconcile each worktree with existing job/task/dispatch records, current writers and owner acknowledgment. Inspect only authorized exact host worker/process/session handles and relevant filesystem/application/Git locks. Record handle identity, observation time, live/stopped/unknown result and actual fence/acknowledgment receipt. A missing PID can be reused or refer to another host; a stale-looking lock or absent worker record is not proof of stopped ownership.
5. Keep unknown-live or owned-active worktrees unchanged. This procedure never force-terminates workers, removes/unlocks locks, force-removes worktrees or prunes registrations. Needed shutdown/fencing must be separately owned and observed under the worker contract before reassessment. Never manufacture an acknowledgment or infer stop from removal of a directory.

### 2. Inventory recoverable state without dropping user work

1. In each authorized worktree, distinguish HEAD bytes, actual index/staged entries including unresolved stages, working-tree modifications/deletions, untracked files, ignored/hidden files, empty directories, modes and symlink targets. Inspect relevant sparse-checkout, skip-worktree/assume-unchanged and filter settings; a clean ordinary status summary may omit real bytes. Capture user ownership and do not stage, stash, reset or clean anything as discovery.
2. Identify nested repositories/submodules and their own HEAD, indexes, local commits, dirty/untracked/ignored state and object availability. Identify LFS pointer versus available payload bytes and any filter/attribute-dependent restoration. A parent gitlink or LFS pointer is not the referenced content. Do not initialize submodules, download payloads or invoke unreviewed filters/hooks to fill gaps.
3. Identify worktree-specific configuration, Git administrative/index dependencies, conflict/merge/rebase/sequencer state, local hooks and required shared objects/alternates. Inspect sensitive configuration only under authorized disclosure controls. Record filesystem features the archive/restore tool can actually preserve, including permissions/ACLs and platform-specific metadata where required; unsupported metadata is a recovery gap.
4. Map known external dependencies such as databases, mounted volumes, credential facilities, running services and external job/evidence stores using existing authorized references. Do not follow links or copy external/private data implicitly. State their actual owners, recovery references and exclusions; a directory archive cannot recover external state, secret access, a running process or remote side effects.
5. Report per component **selected for capture**, **retained separately**, **not preserved** or **cannot archive**, with reason, owner and recovery consequence. Keep private evidence in its existing authorized custody or an explicitly permitted protected copy; sanitized report references are not copies of the original bytes. If private/secret/user state cannot be preserved safely, block destructive removal rather than expose or silently discard it.

### 3. Select keep, archive or remove with exact proof

| Decision | Required evidence and authority | Actual outcome boundary |
| --- | --- | --- |
| Keep | Current bounded inventory and reason; existing owner retains custody, with authentic acknowledgment for any proposed custody transfer | No archive or removal implied; unknown liveness/ownership stays visible and blocks removal |
| Archive | Explicit capture/storage grant, stable selected source, exact preservation/exclusion plan, actual captured bytes/index dependencies and permitted retention/retrieval controls | Archive exists only after capture receipts; recovery is unproven until actual restore succeeds; source remains present |
| Remove | Fresh observed stopped/fenced ownership, exact destructive grant, protected user state recoverable, verified archive/restore and no unresolved locks/dependencies | Only the named linked worktree and its supported registration effect; no branch/ref deletion, prune, unlock, external cleanup or claim of liveness fencing |

For a read-only request, recommend the appropriate decision and identify missing action grants; do not claim it was executed. An archive with excluded disposable files must name them and the owner's explicit disposition. Never classify user changes, unpublished commits or private evidence as disposable merely because Git ignores them. Missing required preservation means keep, not a reduced-scope “complete” archive.

### 4. Capture and prove exactly what is recoverable

1. Before capture obtain observed exclusive stopped/fenced source ownership; coordinate shared Git writers where they could invalidate needed objects/refs/index state. If this cannot be established, retain keep and report a proposed capture only. Freeze exact source identities and inventory, accepted limits and destination. Do not write the archive inside the tree being captured or overwrite an existing backup.
2. Choose and label the real artifact type. A **Git-tracked archive** contains only the selected committed tree. A **Git bundle** contains only its explicitly selected reachable Git objects/refs and may depend on prerequisite objects. Neither automatically includes the index, dirty/staged-only bytes, untracked/ignored files, submodule repositories, LFS payloads, local config, ACLs or external state. Record prerequisites and actually verify availability; never call either artifact a complete recoverable worktree by itself.
3. For a **recoverable worktree capture**, preserve selected actual filesystem bytes/tombstones/modes/link targets plus exact index bytes and required staged/conflict objects, HEAD/refs and administrative state needed for the declared restore. Include explicitly selected untracked/ignored and submodule/LFS payload bytes. Use supported tooling with safe path semantics; inspect filter/hook effects, do not follow escaping links or blindly transplant a shared common Git directory. Capture separately controlled configuration/secrets only with explicit authority. If the format cannot retain necessary state, stop that completeness claim.
4. Record actual artifact locators, raw-byte digests/sizes, manifest and source-to-artifact mappings, creation observations, excluded/not-preserved/cannot-archive state and prerequisite objects. Recheck the frozen source for changes; any mutation invalidates the capture's completeness until reconciled. A digest proves only the captured bytes, not that selection was complete or storage is confidential.
5. Observe actual permitted reader access, retrieval and retention through the required recovery window using the candidate contract. Preserve source index/staging evidence and manifests under appropriate ACLs: path names, logs, object history and indexes may themselves reveal private material. Do not put credentials, secret values or private archive URLs with embedded tokens in ordinary reports. Required encryption needs an actual authorized key-custody/retrieval owner, not a claim that a suffix makes the archive safe.
6. Under explicit restore/extraction authority, retrieve the exact archived bytes into a separately owned approved destination outside live/source/evidence roots, with safe extraction and no hooks, filters or scripts executed implicitly. Reconstruct using the captured artifacts and declared available prerequisites, not uncaptured source files. Compare actual restored bytes, deletions, modes/link targets, HEAD and index/staged/conflict state with the frozen selected inventory; exercise required submodule/LFS and metadata recovery. Record real comparison results and all unsupported state. Merely listing an archive or validating bundle structure is not restore proof.
7. Retain the verified archive and restore receipts before any removal decision. A failed/unrun restore, inaccessible private evidence, missing payload/index objects or unpreserved required ACL/state blocks removal. Keep the original and name the exact missing capability/owner; do not invent restored rows or describe excluded bytes as recoverable.

### 5. Perform only separately approved removal

1. Reconfirm the exact resolved worktree/registration, current owner and lock observations, archive retrieval/retention/restore receipts and action-specific unexpired grant immediately before removal. Any changed source/index/refs or resumed/unknown writer invalidates the old decision. A verified archive is not a lock or an acknowledgment.
2. Use only the host's supported **non-force** linked-worktree removal operation for the exact approved linked path after its real preconditions are met. If dirty, locked, nested state or another safeguard prevents removal, stop and keep it; do not reset/clean files, bypass the refusal, unlock, prune or delete the directory directly. Removal of the main worktree or deletion of branches/refs is outside this procedure.
3. Observe the actual operation result and independently inspect the exact registration/path outcome through authorized host reads. Reconcile partial/ambiguous effects before any retry; an error does not prove nothing was removed. Record archive retained, source retained/removed/partially removed/unknown and remaining ownership separately. Retain shared common objects, other worktrees, user data and recovery artifacts.

## Evidence and completion

Use the configured response template and existing acceptance rows. Return one report-local row per approved worktree: exact repository/path/HEAD/branch; actual user/worker/process/lock ownership and dated observations; tracked/index/dirty/untracked/ignored/submodule/LFS/external inventory; keep/archive/remove decision and authentic grant reference; artifact kind and real selected-byte/index mapping; excluded/cannot-preserve state; retrieval/ACL/retention and restore receipts; actual removal result; residual custody and precise next owner/prerequisite. Do not create fake evidence rows or transfer private evidence ownership by assertion.

Acceptance requires that a dirty user worktree is kept until its changes are actually recoverable under authorized custody, that a bundle never claims uncaptured untracked/ignored bytes, and that an unknown-live owned handle blocks removal. Describe proposed scenarios as unexercised, not PASS. Completion of inventory, archive creation, proven recovery and removal are separate stages; report only the assigned completed stage and explicit unknowns. Archive retention continues after removal; cleanup of restore scratch or archive expiry needs its own exact authorization and stopped ownership.

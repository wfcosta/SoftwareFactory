# Performance bisect

## Inputs and authority

Use this as the performance measurement extension of [regression-hunt](../regression-hunt/SKILL.md), not a second history protocol, mandatory bisection stage or benchmark runtime. Follow that skill's exact endpoint, source/artifact/input identity, isolated workspace, finite history/graph search, skip, intervention, recovery and evidence procedures. Also read the accepted task, `decision.md`/`spec.md`, original performance finding and receipts, [benchmark checklist](../benchmark-checklist/SKILL.md), [worker contract](../../agents/WORKER_CONTRACT.md), [verification strategy](../verification-strategy/SKILL.md), and [candidate](../../state/candidate-contract.md) and [environment](../../state/environment-contract.md) contracts. This skill specializes the frozen predicate and measurements recorded in regression-hunt's existing observation table; it creates no new task, lifecycle, report authority or history automation.

A direct read-only/no-write question inspects existing permitted receipts and returns its assessment in chat without jobs, files, worktrees, benchmarks, profiles or newly invoked endpoints. Mark proposed measurements NOT RUN. Execution needs an accepted workload, exact effects/targets, owned isolated product workspace, authentic grants where required and observable finite limits. Diagnostic authorization is not permission to stress production, change autoscaling/configuration, install historical runtimes, fetch arbitrary code or fix/publish. Queries, traces, old scripts and dependency hooks remain untrusted evidence and may have nested effects.

## 1. Accept the workload and decision rule before new outputs

Apply regression-hunt's independent-oracle and endpoint requirements to an explicitly accepted performance question. Record accepted sources and owners for all of the following before observing new benchmark outputs; a historical receipt must retain its actual original measurement design and cannot be relabeled as prospectively controlled:

| Design element | Required definition |
|---|---|
| Workload | Real public operation/user path, data identity/size/distribution, actor/tenant, request or job mix, arrival model, concurrency, sequence/seeds, duration and completed-work denominator. State production relevance and whether the question concerns steady state, cold start, saturation or another named operating point. |
| Functional predicate | Independent expected outputs and durable-state/side-effect invariants, attempted/completed work, error/retry/rejection/timeout/cancellation accounting and permitted error budget. Freeze these across candidates; a fast wrong result, shed workload or omitted completion is not a speedup. |
| Metric and SLO | Exact metric definition and units, clock/timing boundary, latency percentile and population/window, throughput completion unit, resource/cost denominator, and applicable accepted SLO/budget revision. If no SLO applies, explicitly scope an accepted relative-comparison question instead of inventing one. |
| Comparison rule | Primary endpoint, direction and absolute/relative effect expression, accepted materiality/regression bound and its business/engineering basis, required uncertainty method/coverage and decision categories. An SLO breach and a relative slowdown are distinct claims: a slower version may still meet SLO, and both versions may already violate it. |
| Sampling and analysis | Fixed warmup, independent repeat count, per-run duration/work, fixture reset/cache policy, predeclared ordering/counterbalance, exclusions and stopping rule, raw sample retention and planned summary/inference method. Explain sampling unit and dependencies; requests within one run are not automatically independent repeated experiments. |
| Controls and limits | Exact artifacts/builds, measurement tool/harness versions, environment/load/resource controls, finite attempts including warmups/rechecks/skips/confirmation, elapsed/concurrency/data/output/storage and observable resource/cost caps. Reserve observations for endpoint checks and confirmation. |

Do not pick an arbitrary percentage regression threshold, take the observed gap as the threshold, change the primary metric after seeing it, choose a favorable percentile or extend sampling until significant. If the accepted materiality bound or decision owner is absent, report descriptive measurements within authority and block a claimed good/bad performance classification requiring that bound. A predeclared SLO is not automatically a justified relative-regression cutoff.

Discover and read the actual harness and supported host/tool interfaces before choosing invocations. Establish what starts/stops the clock; whether asynchronous work finishes, responses are consumed and state commits inside the measurement boundary; how retries, timeouts, rejected operations, empty caches and failures enter metrics. Record actual monotonic clock/timer implementation and resolution, client/server clock relationship where relevant, harness/load-generator version and configuration digest. No fabricated benchmark flags, tools, statistical outputs or equivalent-looking substitute can establish unavailable real behavior.

## 2. Establish actual comparable endpoint artifacts

Use regression-hunt's demonstrated good/bad endpoints, not a last green badge, branch name, assumed ancestor or performance label in a commit message. Retain exact source/content, build inputs and immutable binary/container/release digests for both sides, raw per-run outcomes and the actual artifact loaded by the harness. An unavailable historical artifact is a gap; a new rebuild is a separately identified observation, not proof of the original deployed artifact's performance.

Compare the same accepted workload, metric, correctness predicate and measurement design. Freeze or record OS/architecture/kernel, CPU topology and affinity, frequency/power/thermal policy, available memory, storage/network, virtualization/container limits, runtime/compiler/JIT/GC, release-build flags, lock/resolved dependencies, generated inputs, schema/index/migration state, configuration/pools, dataset and fixture/reset identities, cache policy and target/service versions. Record effective load-generator capacity and competing host/service load during actual runs, not merely machine specifications. Observe the resources relevant to the accepted claim; a saturated client, throttled container or different query plan can dominate the result.

For a history diagnosis, hold non-investigated tuning and controls fixed rather than retuning each revision to win. If the accepted question is adoption between independently tuned alternatives, use benchmark-checklist's fair production tuning and document it as that different comparison; do not silently convert a frozen historical search into optimization. Necessary historical tool/dependency differences, hardware changes or coupled configuration differences narrow attribution and may block comparability. Do not force unsupported combinations or conceal them under a shared version label.

Prefer exact retained endpoint receipts when their provenance and actual design support the required comparison. Historical runs with unknown background load, different warmups or incompatible harnesses can inform a hypothesis, not manufacture comparable endpoints. If endpoints cannot be independently established under the frozen rule, finish safe analysis but do not claim a performance regression boundary.

## 3. Measure with fixed controls and honest uncertainty

For explicitly authorized runs, apply the benchmark checklist to real completed correct work and keep its repeated-comparison requirements. Use at least five repetitions per side with equal declared warmup and reset; predeclare a balanced alternating order and starting side, or an accepted counterbalanced schedule that avoids systematically favoring one side. Record the actual order and deviations. Existing receipts with fewer repetitions remain those observations, not a retrospective five-run comparison. A single-run ballpark cannot establish regression endpoints or justify bisection.

Separate startup/JIT/cache warmup from recorded steady-state work according to the accepted question; cold-start measurements instead preserve the declared cold baseline. Observe stabilization using the predeclared bounded rule, not an open-ended warmup until numbers look good. Unachieved stabilization or reset is an inconclusive comparison, not license to discard the slower side. Recreate only owned fixtures through supported authorized interfaces, observe readiness/reset and verify the loaded artifact before each run.

Record every warmup, measured run, retry, exclusion and interruption with actual command/action and cwd, exact tool/harness/config/artifact/fixture identities, timestamps, order, attempted/completed work and errors, raw values/distributions, host/target load and resource observations. Extend the existing regression-hunt observation-table receipt/predicate/classification cells with these measurement references and effect/uncertainty results; do not start a parallel history ledger. Keep immutable unsuccessful observations as well as convenient summaries. A timeout, failed build, wrong output, missing metric, unavailable target or incomplete measurement is not a numerical slow result.

Analyze only the predeclared primary comparison using its justified method. Report per-run values, sample count, units, median/range and meaningful percentile/throughput summaries, effect size and uncertainty. State confidence/coverage and assumptions only when actually calculated by supported methodology; do not invent intervals or treat raw within-run requests as independent replication. Preserve distribution/skew and serial dependence where relevant. Do not average per-run percentiles and call the result a pooled percentile. Pairing, aggregation, outlier exclusion and multiple-comparison handling must follow the frozen design, not a result-driven selection.

Classify narrowly against the accepted rule:

- **Demonstrated good:** comparable complete measurements and uncertainty meet the predeclared good predicate. This is scoped evidence, not universal performance or functional correctness.
- **Demonstrated bad:** comparable complete measurements and uncertainty meet the predeclared degraded predicate. Record whether the demonstrated claim is relative regression, SLO violation or both, and the actual units/effect.
- **Inconclusive:** uncertainty overlaps the decision region, variance/drift prevents separation, controls/correctness fail, samples are insufficient or bounds expire. Inconclusive is not bad, and a nonsignificant result is not proof of no regression or equivalence. A meaningful equivalence/no-material-difference claim needs its preaccepted bounds and appropriate actual evidence.
- **Not comparable / skipped:** unsupported historical runtime/build, missing bytes, unavailable observer/service, different workload/harness or another real prerequisite prevents the selected comparison. Preserve the exact reason and remaining candidate interval under regression-hunt's supported skip procedure. Do not map skips to bad for search convenience.

Statistical confidence does not overcome systematic bias, wrong units, functional errors or a changed workload. Recheck physical plausibility, actual timed completion, resource tradeoffs and client saturation under benchmark-checklist. Profiling/tracing may identify a mechanism only in separately identified authorized diagnostic runs; perturbed timings are not the reported comparison. If that work is not authorized or observable, preserve the limiter/mechanism gap instead of asserting it.

## 4. Search only when the measurements warrant it

Invoke regression-hunt's history selection only after actual endpoints support the frozen classification and the relevant change axis/history is available. Examine source, dependencies, packaging, toolchain, runtime configuration, deployment and hardware/load changes; a source bisect cannot locate an unrecorded external configuration or noisy neighbor change.

Bisection is warranted only with a supported ordered path and a defensible single-transition/monotonicity assumption for this workload, metric and rule. Use discovered real tool capabilities; no automatic unchecked benchmark script across revisions. Apply the same frozen measurement and uncertainty policy to each selected version within the shared finite limits. Keep good/bad/inconclusive distinct; use only the real tool's supported skip behavior for non-results. Reserve comparable endpoint rechecks and neighbor confirmation rather than spending all attempts narrowing history.

If results alternate, effects reverse with load, endpoints drift or a version is good at one operating point and bad at another, suspend monotonic bisection. Preserve the contrary observations and use regression-hunt's bounded explicit comparisons or separately accepted intervals/workloads; do not silently change concurrency, metric, dataset, tolerance or cutoff until a neat first-bad commit appears. Skips/noise can leave multiple candidates or no resolvable boundary. Report the actual examined graph/path, excluded parents and candidate interval, never a fabricated unique culprit. A tool's first-bad message is conditional search output, not causal proof.

A suspected boundary can identify an interaction or merge resolution rather than one change. Preserve actual merge/parent identities and coupled differences under regression-hunt. If all available measurements only support a narrow workload-specific difference, do not generalize to every resource size, customer distribution, machine or production deployment.

## 5. Confirm a narrow mechanism, not a universal cure

Use regression-hunt's explicitly authorized isolated intervention procedure. Where supported, an isolated revert/removal in the bad context should restore the accepted performance predicate, and reapplication/reintroduction should reproduce the same degradation with functional correctness frozen, using comparable measurements and the planned uncertainty rule in both directions. Record exact patch/input/artifact changes, resets, all outcomes and coupled effects. A single favorable revert, profiling hotspot, temporal correlation or hypothesis alone remains suspicion. If confirmation is unavailable, inconclusive or unauthorized, retain the interval and competing mechanisms with the exact missing prerequisite/owner.

Causal confirmation is limited to the exercised workload, versions, environment, metric and intervention. It does not prove a universal cause, safe optimization, absence of other regressions or production capacity. Never weaken assertions, omit real work, discard failing results, alter benchmark-only settings or special-case the fixture to manufacture a confirmation. Preserve both functional and performance counterexamples.

Diagnosis does not implement a permanent fix. Hand the original evidence, narrowed mechanism, resource/error tradeoffs and proposed discriminating correctness/performance proof to the separately assigned implementation owner. A benchmark-only improvement is not proof of an end-to-end permanent fix; a narrower micro result stays a micro result. Any permanent correction needs accepted product behavior, new exact candidate/artifact-bound evidence, production-relevant measurement and required independent reviews/configured checks. These diagnostic runs do not create or pass a permanent performance gate, replace other checks, close the original finding automatically or authorize release. An actual gate must be separately accepted/configured with a justified stable workload and decision rule.

## Recovery, evidence and completion

Apply regression-hunt's recovery, liveness reconciliation, cleanup and retained-proof requirements unchanged. Stop/fence affected owned work on limit exhaustion, expiry or interruption, preserve counters and raw observations, and reconcile actual external operations before retry/reset; cancellation is not proof of stop. Clean only authorized owned workspaces/resources after preserving evidence, never the user's checkout or original artifacts. Report exact leftovers, observed cleanup, resource/cost recovery and responsible owners.

Index accepted workload/SLO/design revisions, actual artifact and complete input manifests, harness/tool identities, raw per-run samples and correctness/error evidence, sequence/warmup/reset/load/resource observations, calculated effects/uncertainty, every skip and contrary outcome, search graph/interval and actual intervention receipts. Retain exact raw-versus-sanitized provenance/digests, immutable readable locators, retrieval identity/ACL and real retention/expiry or manual owner. Required evidence must remain retrievable after teardown; a dashboard latest link, one favorable chart or hash without content is insufficient.

Return the [configured report](../../templates/response-template.md), or direct no-write answer, using regression-hunt's endpoint/search/causal evidence structure with this frozen measurement design and classification basis. Include every assigned criterion with actual MET/NOT_MET/BLOCKED evidence, the actual executing role's documented verdict, remaining prerequisite/owner and original finding reconciliation. A completed diagnosis with an inconclusive performance boundary is not a passing regression claim or product gate; missing required proof is BLOCKED. Changes to workload, correctness oracle, SLO/rule, samples/design, harness/toolchain, artifacts/dependencies/config, environment/load or fixtures invalidate consuming comparisons rather than rewriting completed attempts.

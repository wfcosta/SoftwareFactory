# Mapping publication and deployment to the real host

Use the product's existing runbook and installed interface/version; these are examples, not assumed capabilities or publication/deployment authority. The [release procedure](../SKILL.md) and contracts remain normative. Select its A or B branch first. Do not add a wrapper, pipeline, controller, dependency or executable to this Markdown distribution.

## A — Package registry transport

1. For an actual npm-compatible registry with npm already installed, inspect `npm --version`, `npm help publish`, `npm help view` and `npm help whoami`. Freeze the selected real registry URL in every applicable native request; inspect effective package/publish config, scoped registry overrides, hooks and redirect/auth behavior without exposing tokens. Use the documented authenticated identity query against that registry and provider account/namespace APIs as needed; `whoami` alone may not prove organization/namespace write scope or endpoint ownership. No npm dependency is required or installed by GSF.
2. Use the exact reviewed archive from the immutable build, not a fresh source-directory pack that can run hooks or alter bytes. Independently hash archive bytes using the registry-supported integrity algorithm; inspect actual archive package metadata for exact name/version and index that relationship to source/build/provenance. Query the exact version's metadata/integrity and archive locator before writing; do not resolve `latest`.
3. Inspect the installed transport's actual semantics: native publication may execute lifecycle hooks, apply `publishConfig`, change visibility/access or create/move a distribution tag. Disable only supported unnecessary hooks without skipping required build proof; deny ungranted effects. npm-compatible publication is not automatically create-only merely because it rejects existing versions. Any required alias/tag effect needs its own exact authentic grant; moving a pre-existing `latest` alias is not implied by version publication. If required extra effects cannot be constrained/authorized, block this transport.
4. Use the native publish operation only after A's full gate, immutable-version/ownership proof and persisted intent. Preserve native response, exact registry URL/name/version/integrity and any operation ID actually provided. Retrieve exact-version metadata and archive bytes afresh through authenticated registry interfaces; independently compare integrity/name/version and retrieve required provenance/attestations. Native publish success or `npm view` metadata without byte retrieval is not complete proof. Registry tarball URLs must remain within the accepted receiver/credential boundary.
5. On lost response, query exact name/version and integrity plus actual registry history/audit/operation status if supported. Never immediately rerun publish or bump version. Verify an existing matching archive truthfully; a conflict is denied and an unobservable outcome blocks. Do not use unpublish/deprecate/dist-tag movement as automatic recovery.

## A — OCI registry transport

1. Discover the actual installed OCI client and its version/help or documented supported registry API. Establish authenticated registry endpoint, account/tenant and exact repository namespace from provider identity/access responses and repository inventory. A successful registry `GET /v2/` establishes protocol reachability, not complete account/namespace authority. Follow real auth challenge/credential scope without retaining tokens; deny cross-host redirects or implicit credential fallback outside the accepted receiver.
2. Bind the reviewed image layout/build output to exact registry manifest/index bytes and media types, platform manifests, config and layer descriptors with their real digests/sizes. A `docker save` tar digest or local image ID cannot substitute for the pushed manifest digest. If the client converts media type or recompresses blobs, obtain the actual normalized bytes, provenance and affected artifact proof before authorizing that output. The transport must support the accepted immutable content/version binding; do not use a mutable tag alone.
3. Discover native immutable-version/conditional-write semantics, publication principal scope and effective fencing. OCI blob upload sessions may have native handles; uploading a blob does not publish a manifest/version. Freeze exact accepted blob and manifest operations, including final manifest/version reference and any separately granted alias effect. Registry protocol alone does not guarantee immutable tags or provide a cross-request publication lock. If provider policy/transport cannot prevent unauthorized overwrite, block.
4. Submit only the pinned reviewed content under A's persisted intent. Retain upload/commit and manifest submission responses, observed content-digest headers and operation IDs actually exposed. Read back exact manifest/index bytes by immutable digest, compare native registry digest with independently hashed bytes and verify every referenced manifest/config/layer digest and size, plus required provenance/signatures. For a platform-specific consumer, retain its index→platform-manifest relationship rather than demand equality between different legitimate digest levels.
5. Reconcile interrupted uploads/manifests using actual native session/operation status and exact repository/version/digest lookup before repeat. A missing manifest can coexist with committed blobs or a live upload; stop/fence prior owners and prove disposition. Matching content needs no duplicate upload; conflicting version mapping is denied. Do not delete referenced blobs, manifests or tags automatically. Supported owned upload-session cancellation must be separately within scope and proven not to remove published content.

Both A mappings require fresh policy/observed/grant equality. Region may be null only when authentic provider identity and provider documentation prove no region dimension, never because a registry hostname omits one. Missing publication transport, authentication, immutable identity or required retrieval/provenance is BLOCKED; missing deployment/traffic/health tooling is irrelevant to A. A local HTTP fixture proves only its declared byte-storage/reconciliation contract, not npm/OCI interoperability or a cloud registry.

## B — Deployment hosts

All examples below are B only and retain the full deployment prerequisites, `release.md` state machine, rollout/observation and recovery gate. A package/image publication receipt does not enter these steps.

### Kubernetes example

For a product actually deployed through an authorized Kubernetes client:

1. Establish cluster/account/namespace identity through actual authenticated server and provider reads, not a context display name. Inspect `kubectl version --client`, installed help and the product manifest/rendering toolchain. Match cluster/namespace/workload immutable IDs to accepted target scope, including service account and any cross-cluster dependencies. Read current Deployment, ReplicaSet, Pod, Service and routing objects using explicitly selected context/namespace; `kubectl get deployment <name> -o json` exposes generation, spec and status but may also expose sensitive config values, so sanitize captures.
2. Identify the real environment lock/fencing boundary. Kubernetes optimistic concurrency/resourceVersion protects individual conditional writes; a rollout status watcher is not a deployment lock. Other GitOps/deployment controllers can immediately overwrite a manual change. Use the actual authorized controller's promotion mechanism or establish real exclusive fencing; do not fight it with repeated `kubectl` writes.
3. Render and verify the product's exact immutable manifest/config bundle with its existing toolchain and reviewed inputs. Pin container images by registry digest rather than a mutable tag. Verify all containers/init containers, config/secret version references, rollout settings, storage changes, service account and traffic selector effects. Client/server dry-run can inform validation but does not prove business behavior, lack of side effects or apply authorization; admission webhooks and platform behavior have real prerequisites.
4. Invoke only the authorized supported product operation. If the product's actual documented path is `kubectl apply`, apply the reviewed immutable manifest bundle to the explicit target; do not render fresh unreviewed values inside the effect. If it is `kubectl set image`, use the exact named workload/container and digest with separately reviewed effective config/schema identity. Follow installed help for exact flags. A command accepting an object does not prove pods are running the new image.
5. Use supported `kubectl rollout status deployment/<name> --timeout=<bounded-duration>` as a bounded progress observation, then read back Deployment generation/observedGeneration, available/updated replicas, ReplicaSet ownership and Pod UIDs/status/container imageIDs. Compare the actual imageIDs to the reviewed manifest/index and resolved platform-specific image digests; multi-architecture digest relationships must be supported by registry provenance, not assumed string equality. Read actual Service/Ingress/routing configuration and exposed cohorts.
6. Exercise the actual authorized product probe and telemetry surfaces for the full health window. Ready replicas or a completed rollout do not prove correct requests, queue processing, data compatibility, external dependencies or all traffic reaching the intended version.
7. On interruption, query the existing objects/operations and actual running image/config before retry. A timeout may mean the rollout continues. For recovery, redeploy the known-good reviewed digest/config through the supported controller while checking current schema/data compatibility and authority. `kubectl rollout undo` chooses retained revision state, not automatically the accepted artifact/config; never assume that revision is the verified recovery identity. Confirm running-state and full recovery criteria after any recovery command.

### Managed platform or existing pipeline

- Discover the actual supported release API/console or existing pipeline interface and version, plus its authenticated principal and target binding. A CI provider is not automatically a deployment platform.
- Select an immutable artifact digest and exact config/schema inputs. Retain platform release ID, environment ID, submission request and deployment operation handle. A pipeline run ID proves which pipeline ran only when its recorded inputs/provenance and downstream operation are also observable.
- If the host is GitHub CLI and an existing authorized workflow is the documented deployment path, `gh workflow view`/`gh run view` with installed supported fields can inspect that workflow/run. An authorized workflow dispatch still needs exact immutable input binding, the existing production approval/environment controls and downstream provider receipts. `gh run watch` completing green is not final deployment/health proof. Do not create a workflow or infer deployment from the mere existence of Actions.
- Observe the platform's actual target revision/artifact/config, operation state and traffic/health surfaces after submission. Use its native operation/idempotency lookup on ambiguous return. If the provider exposes no way to prove the running artifact or effective config required by acceptance, report that capability gap and block the affected promotion claim.
- Do not emulate canary delivery by merely waiting between repeated full deployments. Gradual strategy requires actual cohort/traffic controls, representative samples, explicit bounds and safe stopping semantics. Use a supported in-place or maintenance procedure with accepted blast radius when gradual routing is unavailable.

### Manual console operations

A console can be a real authorized adapter when no CLI is supported. Record observed authenticated account/target, selected immutable artifact/config, exact operation and its receipt, screenshots only when useful and permitted, plus subsequent authoritative status and health queries. Do not log cookies/tokens or customer payloads. If a console hides identity, revisions, ownership or durable operation outcome required by acceptance, do not fill those gaps with a narrative success statement.

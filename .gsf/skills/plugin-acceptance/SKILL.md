# Plugin acceptance

## Scope and authority

Use for consumer acceptance of one exported bundle on one exact host/version, not to implement an exporter or infer support for every host. Follow [plugin export](../../docs/hosts/plugin-export.md), [GSF mode](../gsf-mode/SKILL.md), the [worker contract](../../agents/WORKER_CONTRACT.md) and [verification strategy](../verification-strategy/SKILL.md). This Markdown procedure supplies no installer, validator, host tool, hooks, connector registration or model entitlement.

A direct read-only/no-write assessment uses existing permitted files/receipts and answers in chat: no job, evidence writes, export, host invocation, installation or experiments. Label proposed observations NOT RUN. An execution assignment separately names allowed structural reads, export writes if needed, installation/enabling, discovery probes, invocation, removal and owned disposable paths. Permission for one does not grant another; no repair of source, host settings or registrations is implicit.

Use an owned disposable product outside the framework/bundle roots and an actually isolated disposable host profile where supported. A directory named scratch is not isolation. Missing required containment or a safe documented removal route blocks installation; continue permitted structural analysis. Never run a product task in the plugin directory.

## Inputs and prerequisites

- Exact source root/revision and raw-byte inventory identity, companion exporter revision/version and reviewed packaging instructions, selected pack/entries, export recipe and original receipts; an existing export may be inspected without running the exporter.
- Exact bundle root/digest, generated `gsf-package.json`, manifest, source/output hashes, wrapper mapping and applicable notices. Preserve actual field names; do not invent an inventory schema or claim hashes authenticate the publisher.
- Actual host product, exact version/build, OS/architecture, documented native layout and observed available discovery/invocation/removal interfaces. Read installed help and versioned official documentation only through authorized capabilities; no assumed CLI validator.
- Accepted finite consumer criteria; owned product/profile baseline and synthetic inputs; permitted host data/log/network behavior, limits, cancellation, evidence destination and removal owner. Dependencies and installation require separate authority, not automatic bootstrap.
- The **active product** root and its accepted `.gsf/GSF_CONFIG.md`, configured constraints and frozen policy/job baseline where applicable. Bundled reference policy is never active authority. An unadopted product needs separately authorized [adoption](../gsf-adopt/SKILL.md)/[setup](../gsf-setup/SKILL.md) before factory execution, not silent policy copying.

Missing source identity, exporter access, host version, required permission, safe product fixture or evidence capability blocks the affected claim; do not substitute a simulated host or a different host's manifest. Companion access may require an authorized account. Never install dependencies merely to answer a question.

## 1. Freeze finite observations

Record the following table in assigned dispatch evidence, or return its existing-evidence assessment in chat. These are proof rows, not a new schema, gate or policy profile. One row covers one exact bundle/host/version/product configuration; variants require separate rows.

| Observation | Expected consumer predicate | Required evidence |
| --- | --- | --- |
| Structural inventory | Exported bytes correspond to reviewed source and declared selection; excluded private material is absent. | Source/output manifests, actual comparison and inventory receipt. |
| Reference and wrapper closure | Every local dependency resolves inside the intended public reference tree; exposed entries map to canonical instructions. | Resolved reference map and exact wrapper-to-role/skill mapping. |
| Capability delta | No unexpected hook, tool/model permission, connector or host-setting expansion. | Before/proposed/after configuration and permission comparison. |
| Installed discovery | The real host discovers precisely the selected exposed entries under documented names. | Exact host listing/UI receipt and loaded bundle identity. |
| Invoked positive | A selected skill and, when selected, role load the intended instructions and satisfy a bounded consumer request. | Actual invocation, loaded identity and observed response/effect. |
| Invoked no-write | A direct read-only request does not initialize a job or mutate product/factory files. | Response plus scoped before/after product and factory-state comparison. |
| Unsupported/failure | Unsupported support claims are rejected; a bounded invalid/failed attempt is not reported as successful execution. | Authoritative support source, actual rejection or explicit NOT RUN/BLOCKED and residual-state observation. |
| Removed/readback | Only owned registrations/artifacts are removed; discovery and settings readback show the accepted baseline restored. | Native removal receipt, fresh discovery/configuration readback and retained evidence retrieval. |

Bind each row to its criterion, exact source/exporter/bundle/manifest/host/product/policy identity, actor, command or UI action, effect/target and authority, expected/observed result, receipt and limits. Distinguish **structurally inspected**, **installed/discovered** and **invoked**; none implies the next. Required unrun proof is BLOCKED, never PASS. No blanket claim covers other versions.

## 2. Inspect source, closure and exposure

1. Enumerate actual source and output entries, including hidden/ignored paths; compare actual bytes/hashes with the retained source/export inventory using available authorized tools. Reconcile additions, omissions and unstable source rather than trusting Git-ignore rules or inventory assertions. Unknown source files or unresolved correspondence stop structural acceptance.
2. Confirm exporter exclusions against actual source and output: jobs, logs, bug evidence, private model preferences and any other declared private exclusions. Inspect names and permitted metadata without reproducing secrets. Private contents must not survive in wrappers, inventories or copied references; retain sanitized exclusion evidence, not leaked data. Private-source omissions are intentional, not missing public reference closure.
3. Follow every local Markdown/manifest/wrapper reference from its real containing file, including transitive public dependencies and applicable notices. Require the expected complete public `.gsf/` reference tree; reject missing targets, escaping paths, unsafe links/junctions and unresolved case/path collisions. Nonselected reference procedures may remain bundled without becoming exposed wrappers.
4. Compare the selected-entry table and actual exporter support with `gsf-package.json`, native discovery paths and manifest. Inspect every exposed wrapper for canonical skill name or five-pillar role target, unchanged decision authority and supported metadata only. A namespace/alias does not change accepted role identity, create independent review or select a model.
5. Diff requested capabilities against the accepted baseline and reviewed export: hooks, executable launchers, tools/models, permissions, MCP/connector settings, credentials, network endpoints and global/user/project settings. The documented export includes no hooks, permission expansions or automatic MCP registration; an unexpected delta is a finding, not consent. Do not enable it to see what happens.

## 3. Observe the real consumer only under separate authority

1. Preserve structural receipts and baseline product/profile/settings/discovery state outside teardown scratch. Inspect actual host-supported controls and the exact proposed registration scope. Manifest validation, when a real supported validator exists, proves only its documented checks. Record unavailable validation honestly; never invent a Cursor or other host CLI.
2. If installation/enabling is authorized, use only the documented interface for this exact host/version and owned profile. Capture the native result and read back installed bundle/version, enabled state and discovery names. Compare selected wrappers with actual discovered entries and collisions/duplicates; reference-only files must not become unintended exposed entries. Installation success without discovery is not consumer acceptance.
3. If invocation is separately authorized, invoke a selected skill on a finite synthetic request in the disposable product; require an observable response traceable to the intended source instructions. When agents are selected, dispatch one selected canonical role through an actual supported host interface and inspect role identity, five-pillar assignment and report-local ownership. Do not claim a new session proves independence; preserve mandatory independent review separately. Missing role invocation capability blocks that required row.
4. Invoke a direct read-only question with an explicit no-write boundary. The consumer answers without job initialization, product edits, factory evidence or installation/repair attempts. Compare all accepted product/factory paths before/after, not only tracked files. Authorized host-owned transcript/settings writes are separately declared observations, not product no-write proof or permission for additional host mutations.
5. For unsupported hosts, inspect authoritative format/support sources: the documented exporter asserts Cursor/Claude layouts, not Devin/terminal-native plugins. Do not rename a manifest, issue a fictional command or infer support from Markdown readability. If rejection execution is authorized and a real exporter/interface exists, record its bounded unsupported-selection rejection in owned scratch; otherwise mark execution NOT RUN without claiming observed rejection. Unknown version support is unknown, not unsupported.
6. Exercise one accepted bounded failure using a separately authorized disposable copy/profile, such as a missing local reference rejected before loading or a documented invalid manifest. Preserve the original bundle; never corrupt user installation. Observe the actual validator/host error, discovery/invocation status and residual registrations/files; a failed validation is not an invoked negative case. If no safe failure interface exists, block that required proof instead of fabricating it.

## Recovery, report and completion

Stop on unexpected permissions, hooks, scope changes, lost isolation or uncertain liveness. Preserve failed/partial receipts and reconcile actual host registration/session state before retrying. Stop only captured owned sessions; do not globally reset a host, remove user plugins or blindly reinstall after a timeout. Any repair needs new scope and invalidates affected proof.

Under separately authorized removal, use native documented disable/uninstall controls for the exact owned registration; delete only owned temporary paths after evidence retention. Freshly list discovery/registration state, inspect relevant settings/permissions and confirm the accepted baseline and unrelated plugins remain intact. Deleting the export directory alone does not prove removal. Retrieve retained receipts after teardown; unknown registration or active-session state remains BLOCKED with a named recovery owner.

Return the existing executing-role verdict/report binding, not a new plugin-specific role or gate. Include finite row outcomes, exact identities, source and private-exclusion evidence, canonical exposure/permission diff, structural versus installed versus invoked scope, all failed attempts, no-write observations, removal/readback and residual ownership. Cite exact file/revision/line or immutable receipt locators; separate inspected facts, exercised behavior and inference. Retain sanitized evidence with raw-versus-retained provenance, retrieval/ACL/retention limits. Never retain secrets or private host transcripts by default.

A required observed violation is FAIL for checks (or the assigned review role's CHANGES); missing required proof is BLOCKED. A structural-only result cannot accept installed/invoked criteria. Bundle/source/exporter, wrapper/manifest, host/version, permissions, product policy/configuration or fixture changes invalidate dependent observations. Acceptance neither installs anything elsewhere nor grants publication, merge, deployment or broad host support.

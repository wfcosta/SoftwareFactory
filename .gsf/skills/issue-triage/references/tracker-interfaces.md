# Real tracker interfaces and integration limits

Use the product's existing authenticated tracker tool/API/console. These examples describe supported interfaces to discover, not tools available in every host or permission to call them. Read installed help/version and verify the actual service host, API version, principal and immutable repository identity. Apply the [triage skill](../SKILL.md) before every effect; never place tokens in a command line, evidence file or query string.

## GitHub CLI and API example

If GitHub CLI is installed and the selected tracker is actually GitHub:

1. `gh --version`, `gh auth status` and `gh repo view --json id,nameWithOwner,url` identify tool, authentication status and selected repository. Do not use token-printing flags or copy credential-bearing output. Choose the explicit authorized host/repository; a local remote URL alone is not its server identity.
2. `gh issue view <number> --repo <owner/repository> --json id,number,url,title,body,state,author,assignees,labels,comments,updatedAt,closedAt` is useful initial retrieval. Check installed `gh issue view --help` for supported fields. Do not assume a nested comments connection or rendered UI includes all pages, revisions, attachments or hidden content.
3. For full API retrieval, use the documented `gh api --hostname <authorized-host> repos/<owner>/<repository>/issues/<number>` and `gh api --hostname <authorized-host> --paginate repos/<owner>/<repository>/issues/<number>/comments`. Inspect actual pagination completion, status, headers and limits; `--paginate` handles paginated endpoints, not automatically every nested GraphQL connection. Use separately authorized documented endpoints/connections for linked pull requests, timeline and available revision history. Record fields actually returned and unavailable history rather than inventing revision access.
4. Compare returned `repository` identity through the repository API and issue `id`/`node_id`, ordered comment IDs and revisions, `updated_at`, state and available conditional-read headers before/after multi-page retrieval. API issue endpoints can also represent pull requests; distinguish the actual object type. Attachments may require separate protected retrieval and byte limits.
5. Search is a discovery index, not an atomic dedupe lock. `gh issue list`/`gh search issues` and corresponding PR queries must use explicit repository/state/scope and supported pagination/limits. Fetch full matched reports/PRs and inspect actual merge commit and current artifact before claiming an existing fix. A CLI default limit is not an exhaustive result set.
6. If publication is separately authorized, supported operations include `gh issue comment`, `gh issue edit`, `gh issue close` or the documented API mutations. Inspect their current help and scope first; supply exact approved content and IDs. These commands do not create generic exactly-once semantics. Keep the returned remote IDs, re-query the authoritative issue/comment and reconcile ambiguous calls before any retry. Do not use force/admin shortcuts or overwrite a newer human edit.

Other trackers need their own documented immutable project/report IDs, full pagination and revision behavior, principal/permission discovery, write operations and readback. Do not mechanically translate GitHub command names into another service or claim inaccessible history was read.

## Webhook authentication and replay example

For an existing GitHub webhook receiver, GitHub supports an HMAC-SHA256 signature over the original raw body in `X-Hub-Signature-256` when a webhook secret is configured. Require the actual trusted receiver to verify it using its protected configured secret and a timing-safe comparison before parsing or dispatching. Bind the expected installation/repository/event/action separately; a valid secret for one receiver is not broad action authorization. Retain verifier/key-version references and redacted verification evidence, not the secret, raw authentication header or sensitive body.

`X-GitHub-Delivery` provides delivery identity and `X-GitHub-Event` provides event type, but do not claim a timestamp freshness guarantee or cryptographic binding for arbitrary transport headers merely because the body has a signature. The trusted integration must preserve observed transport provenance, impose an accepted receipt-age policy, durably deduplicate deliveries/actions and re-fetch authoritative current state before effects. Deduplicate the verified raw-body digest and immutable authoritative source revision plus approved action/content identity independently of the delivery header, so replaying signed bytes under a different claimed delivery ID cannot repeat the effect. Account for official redelivery behavior, retries and replay-record retention. Body signature validity alone cannot prevent replay of old signed bytes. On uncertain delivery identity or conflicting payload, quarantine and use a separately authorized direct authoritative fetch; never let it automatically publish.

For any other integration, inspect the provider's actual signature/token/OIDC mechanism, audience/issuer and key rotation rules, signed timestamp/nonce guarantees if present, replay window and retry semantics. Use its existing trusted verifier and durable state controls. No verifier, receiver or scheduler is supplied by Markdown. An unsigned forwarded JSON blob, issue attachment or worker assertion is not an authenticated webhook.

## Bounded event operation and privacy

- Accept only configured event types/actions and explicit immutable repository scope. Set payload/page/attachment/event-count and elapsed bounds before retrieval; over-limit content is incomplete, not successfully triaged.
- Use the actual platform's queue/delivery/lock controls if present. Record acknowledgment and retry/dead-letter behavior; do not invent a queue or guaranteed redelivery. Durably reserve dedupe/intent before external effects and acknowledge delivery only according to that integration's real recovery semantics.
- Preserve source/event ID, source snapshot digest, approved action/content digest and remote effect identity in the real integration's single-publisher dedupe tracker. Coordinator-owned indexed Markdown receipts describe/retrieve it; they are not an atomic receiver database.
- Scope event replay retention to actual retry/redelivery and operator replay horizons. If old events can be replayed after records expire, require fresh authorized triage and current-state checks; never interpret expired dedupe as permission to repeat the prior effect.
- Restrict capture and exports to necessary metadata. Private/security reports use approved restricted storage/channels; a public link or signature does not permit copying confidential content into public evidence.

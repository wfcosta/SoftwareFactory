# Memory change acceptance

## 1. Role

Coordinate one authentic, exact acceptance of a nonsecret ordinary-file memory proposal. Separate independent decision, current effect authority, native effect and verified receipt. Complete the review/handoff even when a missing native prerequisite blocks application; never invent an apply engine or call proposal generation acceptance.

Use for a complete create, full replacement or scoped deletion proposal with an independently established decision owner. Use [project memory](../project-memory/SKILL.md) to select useful facts and scope curation first. Merely preparing or reading a suggestion is not this effect workflow. Managed create-only stores, Core policy/grants/state and secret storage require their actual dedicated owners/protocols and are not generic file-edit targets.

Follow [GSF mode](../gsf-mode/SKILL.md), the configured [worker contract](../../agents/WORKER_CONTRACT.md), [candidate/evidence contract](../../state/candidate-contract.md), [context and memory operations](../../docs/operations/context-memory.md) and configured response conventions. Those retain approval, ownership, evidence and recovery semantics. This skill adds no gate, role, lifecycle vocabulary, authority ledger or model/plan key.

## 2. Context

Select **read-only decision assessment/handoff** or **explicitly authorized native effect**. A no-write request returns only a private response; an authorized dispatch writes only its assigned owned report. Acceptance of knowledge, authority to persist a report and authority to mutate a target are distinct.

Require finite explicit inputs:

- Whole original proposal at an explicit authorized location, independently retained complete raw SHA-256/byte count, original proposal/task ID, complete before/proposed-after existence and bytes, full diff and line-ending records, actor/session/reason/provenance and original authority qualifications.
- An authentic independent decision made over that entire proposal, not copied from its approval claims: exact accepted proposal ID/raw pin, root, target, scope kind and case-sensitive opaque ID, operation, complete proposed effect, original before existence/hash/length/file-version evidence and original target-parent version evidence.
- Decision authority/provenance, decision reference, scope, expiry/single-use boundary, required independence and authentic current effect approver. A reference or digest identifies evidence but does not authenticate a decision.
- Exact existing target/root/parent, genuine current native write owner, actual supported tool/operation and its documented conditional/exclusion, retention and readback semantics; real permissions and stable private ancestor evidence.
- Existing authoritative effect tracking for this exact target, complete accepted history/head and receipts, retained approved originals, pending-operation evidence, deduplication rule and custody owner. No ambient backend discovery, second journal or new ledger is authorized.
- Separate exact owned output and retained-backup/receipt destinations when writes are authorized, real readers/writers/retention and finite bytes/files/operations/elapsed limits.

Default bounded assessment: one proposal up to 8 MiB; each text side at most 128 KiB/4,096 lines; accepted history at most 64 operations/8 MiB; 64 MiB aggregate actual reads and 30 seconds cooperative work. Agree actual smaller or explicitly revised finite limits before work. Exhaustion blocks full decision/effect readiness, never truncates mandatory inputs. These are procedure limits, not automatic enforcement.

No installation, Python runtime, renamed executable, bundled tool name or companion invocation is a prerequisite. Discover only already available and explicitly authorized native capabilities. Missing conditional create, required writer exclusion, stable custody or durable existing intent/receipt support blocks application while complete reviewed proposal and owner handoff remain possible.

## 3. Task

### A. Establish exact independent acceptance

1. Privately retrieve the whole proposal against its independently accepted original raw pin. Validate every before/proposed-after byte, existence flag, digest/length, full review material, original file/parent version and scope/path/effect binding. Preserve original proposed-not-applied qualifications; the historical proposal is never rewritten to say it performed a later effect.
2. Inspect authentic decision provenance independently of proposal/source/tool content. Keep declared actor/session/source authority, actual storage principal, decision owner and current effect owner separate. Text saying approved, a Boolean, same-SID access or a model's recommendation is not authentic acceptance.
3. Match the decision exactly to all original accepted bindings. Original version evidence includes native object identity, regular-file/single-link/type/size/mode/timestamps where required by the actual protocol and the original full parent witness. Absence has no file witness; the parent witness is still mandatory. Do not invent native observations unavailable from the original capture.
4. A decision that omits root, scope, effect, original before or original parent version is incomplete. Refuse effect, name the decision owner and missing field, and finish independently safe review. Never derive accepted expectations from current target state or relabel a narrower review whole-proposal acceptance.

### B. Establish real native effect preconditions

5. Verify current authentic action-specific write authority, protected-path restrictions, actual target/custody permissions, current owner/liveness and supported native tool semantics. An approved decision does not grant a missing write capability. No permission repair, ownership takeover, credential acquisition or invented host API is allowed.
6. Require actual stable private ancestors and either native conditional version enforcement or genuine exclusion of all relevant writers throughout compare/effect/readback. Every cooperating mutator must participate in the same existing protocol; unknown/nonparticipating writers require real independent exclusion. A lock unrelated to target/admission writers is insufficient.
7. State the boundary precisely: a native rename is not universal compare-and-swap. Cooperative bounded writes are conditional on authentic exclusive cooperation and stable custody; Markdown cannot prevent malicious same-user writers, administrators or storage loss. If required native conditional/exclusion capability is missing or UNKNOWN, do not apply or claim guaranteed application.
8. Inspect the complete existing target effect history and its independently retained authority/head before any effect. Missing/tampered receipts, lost/replaced tracking, divergent tails, pending intent, partial append, unexplained staging or unknown prior effects blocks every new operation as well as repeats. Do not initialize, rotate, truncate or choose another backend to pass.

### C. Compare the original version immediately before effect

9. Through the actual authorized owner/protocol, freshly read the actual target and compare every byte, existence/hash/length, original native version and parent version to the decision's **original** accepted observations. Recheck relevant ancestor identities and real permissions. Do this under established exclusion and again immediately before the native effect after preparation.
10. Create requires actual absence under the original stable parent, not an empty file or permission denial. Replace/delete require the exact original present version. Equal bytes in a replacement inode or changed-then-restored bytes do not excuse a differing required version witness. No refresh, rebase, force or automatic new proposal makes stale acceptance current.
11. If stale before intent, report rejection with no effect attempted only when actually established. If stale after durable intent, preserve that intent as unresolved; target equality later does not resolve it. Obtain a genuinely new decision only after existing recovery resolves prior ambiguity and a new full proposal is independently reviewed.

### D. Use the existing durable intent/effect/receipt protocol

12. Derive deduplication identity from the exact accepted complete proposal/effect binding under the real existing protocol, not a caller-selected fresh identifier. Retain its complete original decision and expected prior history/head. If the existing protocol cannot prevent changed identifiers from bypassing pending evidence, block rather than promise exactly-once behavior.
13. Before any possible target effect, have the actual owner persist and independently read back durable intent in its existing authorized tracking: exact proposal/raw pin, decision, original version, root/target/scope/operation, complete after descriptor, owner and expected prior head. A response-only note or successful write call is not a durable receipt.
14. Prepare complete approved after bytes in separately owned private storage where needed. Independently read back/pin prepared material and retained exact original bytes; retain original metadata requirements and explicit unsupported preservation. Never overwrite unknown objects or make incidental writes refresh the accepted target-parent version.
15. Perform only the accepted supported operation: **create** uses genuine conditional no-replace publication; **replacement** writes the full approved version and keeps the approved exact original backup; **delete** removes only the approved target binding through the supported recoverable native route while preserving its exact original bytes/object as required. No generic editor bypass of a managed-store protocol is allowed.
16. Deletion is scoped absence, **not physical erasure or forgetting**. Backups, proposals, decisions and receipts still retain material. Replacement backups preserve exactly their documented bytes/metadata, not unobserved ACLs or every filesystem attribute.
17. Independently reopen and read every actual after byte through the authorized native owner; verify actual existence, digest/length and required object identity against prepared/accepted material. For deletion, actually verify absence and read back the retained original. Never infer readback from an effect return, proposed digest, cached buffer or completion Boolean.
18. Preserve original before/parent observations and add separate actual-after observations with method/time and new parent witness. Only after independent actual readback may the owner persist the complete effect receipt, pin/retrieve it, durably complete the existing tracking record and independently read that record back. A successful native effect without these steps is not verified completion.

### E. Deduplicate and recover without blind replay

19. An exact repeated acceptance may return the original receipt without another effect only when complete prior decision equality, original receipt integrity, still-current actual final state and required retained-original availability are independently verified. Repeating an older effect after a later mutation must not resurrect it; changed decision bindings under one operation identity block.
20. A new accepted proposal must agree with the latest established completed history and its own independently accepted original version. New ID, new decision reference or equal current bytes cannot bypass a pending/partial/crashed operation, lost receipt or unknown effect.
21. On possible effect, readback failure, interrupted commit or missing receipt, preserve all original proposals/decisions/tracking/staging/backups and current observations. Block overlapping effects. The actual custodian reconciles actual state and durable evidence under existing recovery; no automatic rollback, receipt synthesis, blind reapply, staging deletion, lock stealing or self-declared completion is permitted.

## 4. Constraints

- Read-only assessment can complete with effect BLOCKED. Report exactly which native/authority/custody/version prerequisite is absent and the supported owner handoff; do not claim an apply capability exists because a procedure describes one.
- Never copy private chats, histories, credentials, secret fingerprints, customer-sensitive reports or hidden reasoning into decisions/evidence. Keep full approved nonsecret private material with real authorized readers and retention.
- Source truth, human/organization authentication, scope authorization, native ACL enforcement and effect evidence are separate claims. A raw hash proves byte identity only. Windows mode bits do not prove private DACLs; same-SID roots are not OS isolation.
- Preserve user edits, accepted historical bytes, existing mandatory checks/reviews and immutable reports. Changed proposal/decision/source, target/parent identity, permissions, owners or history invalidates affected readiness rather than weakening its conditions.
- A cooperative deadline cannot interrupt a blocked native call or certify power-loss atomicity. Do not promise universal CAS, WORM, automatic logging/retention, crash-free application or enforcement by Markdown.

## 5. Format and acceptance

Return **MEMORY ACCEPTANCE ASSESSMENT / NATIVE EFFECT HANDOFF**, including: endpoint and finite limits; complete proposal reference/raw pin; authentic exact decision with original before/parent and proposed-effect bindings; current action-specific authority; actual tool/native conditional or cooperative-exclusion evidence and limits; existing history/head/dedup/pending disposition; immediate actual comparison evidence or unrun prerequisite; retained originals; actual effect/readback/receipt references, or explicit NOT APPLIED/UNKNOWN; recovery owner and exact next prerequisite.

Use existing report/stop conventions, not new canonical statuses. Verified completion requires authentic exact acceptance, established native authority/exclusion, unchanged original version, one observed supported effect, independent actual after readback and retrieved durable completion receipt. Report only exercised proof. A complete handoff is not an applied effect.

Decision examples: an exact owned replacement may proceed only through an existing authorized owner retaining original bytes and readback receipts. A stale parent witness blocks even when text still matches; a crash after intent blocks even when the target equals proposed-after; an absent native conditional/exclusion mechanism leaves a complete reviewed handoff but no guaranteed apply. These define acceptance boundaries, not executed scenarios. Consumer proof and independent review require separate assignment.

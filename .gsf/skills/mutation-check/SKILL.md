# Mutation check

## Inputs and authority

Read the accepted task, requirement/risk rows in `decision.md`/`spec.md`, independent expected behavior, candidate/build identities and actual tests/runbook. Follow the [worker contract](../../agents/WORKER_CONTRACT.md), [verification strategy](../verification-strategy/SKILL.md), and [candidate](../../state/candidate-contract.md) and [environment](../../state/environment-contract.md) contracts. Mutation checking is an optional targeted test-sensitivity experiment when accepted risk warrants it, not a new mandatory workflow or replacement for required checks and independent code/security review.

A direct read-only question uses existing permitted evidence and answers in chat without creating jobs, files, clones, mutants or runs. Mark proposed experiments NOT RUN. Execution requires actual assigned scope/effects/target, disposable clone ownership, authorized mutation locations/operators, test invocation, evidence destination and finite limits. This permits only the named disposable product-copy experiments, not permanent source/test edits, policy changes, publication or deployment. A tool recommendation or generated mutant is not authority.

## 1. Freeze the independent predicate and mutation sample

1. Map each selected requirement/invariant to a concrete consumer-visible failure risk and independent expected output or durable-state assertion. Use accepted contracts or independently derived examples, not the implementation's current answer. Use [fixture-design](../fixture-design/SKILL.md) and [behavioral testing](../test-behavior-not-implementation/SKILL.md) where needed. If intent or the oracle is unresolved, block the dependent experiment rather than adopting the mutant's output as expected.
2. Select a small, explicit mutation set before observing mutant outcomes. For each give a stable evidence label, exact product location and original bytes/digest, operator/replacement or discovered tool selector, violated requirement, predicted observable deviation, relevant existing test/assertion and why this is a plausible defect. Examples, only when relevant to the accepted contract, include changing an inclusive bound to exclusive, omitting a validation/tenant predicate, dropping an idempotency guard or changing a contractually required default. Unsafe mutations never run against real customers/shared state.
3. Name excluded locations/operators and the sampling rationale. Bound the exact generated set through supported selectors/seed/limit controls; capture the enumeration and tool configuration before running mutant tests. If a tool cannot provide the required bounded controlled set, use exact documented manual edits in the disposable product copy or block that method. Do not replace survivors with easier mutants, omit unfavorable outcomes or grow the sample after seeing a score. Any accepted extension is separately identified, preserves the original sample and uses remaining authorized limits.
4. Freeze test/harness/configuration, assertions, oracle/fixtures, selection/order/seeds, timeouts/retry policy, toolchain/runtime/OS, dependency resolution/content, build/generated inputs and real service/environment identities. Record the exact source candidate and loaded artifact. No mutation of tests, assertions, golden files, policy, test-selection rules or harness to obtain kills/passes. A legitimate oracle/test defect requires a separate accepted correction and new baseline; earlier outcomes remain evidence.

Set numeric mutant/attempt counts, elapsed/build/test deadlines, concurrent owners, output/storage and observable resource/cost bounds, including baseline, resets and any runner retries. Choose confirmation work within those limits. Counters persist across handoffs/interruption; unknown metering is not free execution. This procedure runs one mutation at a time with one owned mutable experiment state; do not accept a tool's default parallelism or higher-order combined mutants.

## 2. Discover and isolate the actual execution path

Discover the repository's real test/build commands and the host's actual tools/versions. Inspect the candidate's setup/teardown, package scripts, hooks, generators, links/submodules, mutation-tool plugins and nested effects before execution. Use an actually supported mutation tool with its real invocation/options, version and operator semantics, or record exact before/after edits and their application/reset steps. Never invent flags, install an unrelated tool without authority, ship a hidden runner in Markdown or infer that a command is safe because it is called a test.

Allocate an exclusively owned external clone outside the user's checkout and policy/job roots. Populate it from the frozen effective candidate, including dirty/untracked/ignored/deleted inputs and submodule content as required by the candidate contract; a clean clone of HEAD alone may omit the assigned candidate. Prove complete source correspondence before experiments and record full additional input/output/artifact manifests. Never mutate, stash, reset or clean the user's checkout. Record actual filesystem/process/network/credential boundaries and cancellation/fencing controls; a clone path is not a sandbox. Missing required isolation blocks execution.

Bind each external dependency/resource to actual owned fixture/tenant/account/region/resource identity, readiness, reset and cleanup observations. Local operations use null target; external writes/destruction require fresh exact identity, authentic action-specific authority and actual platform safeguards for setup, mutant behavior and teardown. Consider what the mutation disables: removing authorization or deduplication may cause forbidden data access, duplicate delivery or real charges. Do not rely on the guard being mutated as the experiment's safety boundary. Use synthetic data and independently enforced non-delivery/isolation controls; if unavailable, do not execute that mutant. Mocks establish only their named boundary, never real-service safety or consumer behavior outside it.

## 3. Establish an actual clean baseline

From the verified unmutated input and clean owned fixture, build through the discovered authorized path and run the frozen relevant tests. Capture the exact command/cwd, identity set, start/end, actual exit/stdout/stderr, test enumeration, assertion results and actual loaded artifact. Verify the required tests were collected and assertions exercised; zero tests, a stale binary, setup-only success or a prose PASS is not a baseline.

A failing, flaky, interrupted or unavailable baseline blocks dependent mutant interpretation. Preserve failures and use [flaky-test-investigation](../flaky-test-investigation/SKILL.md) when separately assigned; do not retry until green or alter tests/timeouts to start scoring. An existing authentic baseline can be reused only with the verification strategy's complete dependency/evidence proof, never merely because the command or HEAD matches. A selected diagnostic test set does not replace the configured full gate.

## 4. Run, observe and reset each mutant

For each preselected mutant, in order:

1. Verify the clean source/input/harness/fixture baseline matches its frozen manifest. Apply exactly the named product mutation in the owned clone, capture the exact diff and mutated content identity, and verify no unrelated input, test, oracle or policy changes. A tool-generated edit must be inspected as actual bytes, not trusted from its operator label. One conceptual mutation may involve a documented coupled edit, but do not stack independent changes.
2. Build without stale mutated or baseline outputs, verify the loaded artifact corresponds to this mutant and invoke the same frozen tests/harness. Hold fixture, dependency/config, order/seed, runner retries and observation predicates fixed. Record unsupported controls and confounding. The mutation tool's summary is evidence to inspect, not a verdict to accept blindly.
3. Capture raw build/test outcomes, failure phase, assertion/case IDs and expected/actual public behavior before reset. Keep runner retries, interrupted attempts, setup errors and contradictory outcomes. A tool may count a process crash as killed; retain its original label and report the narrower classification below with the actual reason.
4. Stop or fence owned execution and reconcile any external operation before reset. Restore the exact unmutated product bytes/modes/links, discard/rebuild only owned derived outputs through authorized steps, reset the owned fixture and verify complete baseline input/harness/fixture equality and absence of stale mutant artifacts before the next mutation. Record actual reset receipts. If reset/equality is unproved, stop dependent runs; do not carry a contaminating mutant forward.

Use observation rows in the existing assigned report and indexed evidence, not a new canonical ledger or verdict vocabulary:

| Mutant / requirement | Exact edit and original/mutated identities | Baseline, frozen test/assertion and tool/fixture references | Invocation/cwd and raw outcomes | Classification and causal rationale | Reset/equality proof | Limits / remaining gap |
|---|---|---|---|---|---|---|

## 5. Classify without converting accidents to kills

These are experiment classifications, not task states or role verdicts:

| Classification | Required interpretation |
|---|---|
| killed | A relevant independently grounded assertion actually fails because the mutant causes the selected requirement's deviation, while the comparable unmutated baseline passes. Identify the assertion and consumer-visible expected/actual difference. A generic crash, tool exit, unrelated failing assertion or build/setup failure alone is not a kill. |
| survived | The mutant was built and loaded and the frozen selected tests actually completed without detecting it. This means no detection in that scope, not correctness or equivalence. A runtime crash/infrastructure error without a relevant failing assertion is inconclusive, not survived. |
| invalid-build | The mutation fails compilation, type checking, linking or required artifact construction. Preserve the failure and distinguish an invalid edit/tool mismatch from a meaningful behavioral mutation. It is neither an assertion kill nor a survivor. |
| timeout | The predeclared safety deadline was reached. Preserve liveness/output and reconcile ownership. A tool's timeout-killed label is not an assertion kill; a suspected loop is a hypothesis unless the required causal behavior is independently observed. |
| notrun | No invocation was attempted, for example because a required prerequisite or grant is unavailable. Keep the planned mutant and exact blocker visible; this is not a survivor or kill. |
| inconclusive | An invocation was attempted but setup failure, interruption or a generic runtime crash without a relevant assertion prevents interpretation. Preserve the attempted phase, effects and raw receipt; do not label it notrun, killed or survived. Classify an actual safety-deadline expiry separately as timeout. |
| possible-equivalent | An executed survivor is plausibly behaviorally equivalent within stated reachable inputs/assumptions. Retain its survivor origin and concrete analysis; equivalent is not the default explanation for survival or an automatic exclusion. Missing reachability/semantic proof remains an uncertainty. |

For every survivor, trace the actual product-to-consumer path: was the changed branch reached by the frozen fixtures, was the mutant artifact really loaded, did the state/output differ, and was that difference asserted at the relevant public boundary? Correlate an authorized real observer or existing receipt with the unchanged oracle. Separate missing input coverage, missing assertion, unreachable code under evidenced preconditions, instrumentation/load failure, and genuinely plausible equivalence. Mere code coverage or the absence of a failure cannot choose between them. If additional probes are not authorized or bounded, record NOT RUN and the exact missing proof rather than inventing causal analysis.

Propose a requirement-linked discriminating test/fixture or product correction to the appropriate owner; do not edit permanent tests/product or weaken an assertion here. A confirmed test gap is a finding even if this diagnostic assignment completes. Separate accepted fix work must preserve the original mutant/oracle/outcomes, establish a new clean baseline, exercise the retained counterexample and run all affected configured checks/reviews for the new candidate.

## 6. Report the denominator and reconcile ownership

Report the preselected total and counts for every classification, original survivors and possible-equivalent annotations, all exclusions and their evidence/rationale. Every selected mutant must remain accounted for exactly once in the primary totals; possible-equivalent is a disclosed annotation/reclassification of an observed survivor, never a double-counted extra observation or a silently removed row. If reporting a detection ratio, state the exact numerator and denominator explicitly, such as assertion-killed divided by assertion-killed plus executed surviving mutants, keeping possible-equivalent survivors included unless separately justified and showing both views when excluded. Invalid-build, timeout, inconclusive and notrun counts stay visible outside that ratio; if the denominator is zero, report it as undefined. Preserve the tool's differently defined raw score beside, not instead of, this explanation. Do not compare ratios across different scopes as if comparable or promise a universal quality threshold, complete test adequacy or product safety from a bounded sample.

On interruption, limit exhaustion, identity/authority expiry or unknown liveness, checkpoint receipts, counters, mutant/reset state and owned handles; stop/fence affected work through real controls. Reconcile external intent/operation/resource state before retry or cleanup. Cancellation/timeout alone is not stopped ownership. Resume only with verified baseline/restored prerequisites and current authority/limits, without overlapping possibly live work or rewriting a completed dispatch.

Preserve sanitized required evidence outside teardown scratch with exact raw/retained digests and provenance, immutable locators/run/artifact IDs, retrieval identity, actual ACL and retention/expiry. Then stop owned processes, restore diagnostic controls and delete only the authorized owned clone/fixtures/resources after reset/reconciliation. Record real cleanup and exact leftovers/recovery owner; do not destroy original CI artifacts or user/shared state. Retrieve required retained bytes after teardown; a score badge, mutable latest link or unreadable hash is not retained proof.

Return the [configured report](../../templates/response-template.md) or direct no-write assessment with the requirement/oracle-to-mutation plan, actual baseline, frozen identities/tool interfaces, every raw outcome and classification, survivor causal analysis and uncertainty, explicit totals/denominator/exclusions, reset and cleanup receipts, limits and proposed owner/action. Cover each assigned criterion with its actual evidence and use the executing role's existing verdict. A completed mutation diagnosis does not pass the product/check/release gate, authorize changes/publication or erase original findings; unavailable required proof remains BLOCKED. Source, test/harness/oracle, build/config/dependency, fixture or environment changes invalidate dependent results and require newly bound evidence, not edited historical outcomes.

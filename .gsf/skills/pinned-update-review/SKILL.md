# Pinned update review

## Role

Review one accepted immutable update proposal using the existing [upstream sync](../upstream-sync/SKILL.md) procedure rather than establishing another updater. This skill specializes pin integrity, full reviewable change and native dependency compatibility for distributed/adopted capabilities. It is not an update client, resolver, installer, automatic refresh service or grant.

Follow the [worker contract](../../agents/WORKER_CONTRACT.md), [candidate evidence](../../state/candidate-contract.md), [configuration](../../state/config-contract.md) and [environment](../../state/environment-contract.md) contracts. Reuse [license dossier](../license-dossier/SKILL.md), [curation authority](../skill-curation-authority/SKILL.md), [supply-chain review](../supply-chain-review/SKILL.md), [dependency upgrade](../dependency-upgrade/SKILL.md), [plugin acceptance](../plugin-acceptance/SKILL.md) and the [authorized upgrade guide](../../docs/upgrades/README.md). Those remain the canonical legal, source/customization, dependency, consumer and policy-upgrade owners.

Direct no-write questions return chat from supplied or already authorized immutable sources without jobs, files, fetch/download or native calls. A dispatch writes only its assigned owned Markdown review. Network retrieval, candidate edits, rebuild, install, registration, native execution, publication, merge and deployment each require separate existing owner/tool authority. Assessment does not perform them.

## Context

Freeze accepted reason, target installation/product and complete component/use/recipient set. Obtain authentic adoption/update/customization/distribution decision owners, baseline policy/candidate/environment where applicable, allowed source/installation paths and source-to-package/wrapper mapping. Obtain:

- Old imported upstream exact commit/archive identity, original authentic locator and transformation/import mapping.
- Current local baseline revision and effective local bytes/customizations, including staged/dirty/untracked/ignored/deleted components where applicable; installed package/wrapper version/digest and current accepted trust record separately.
- New upstream exact immutable commit/archive/content identity, full source snapshot, authentic release/migration/provenance/license documents and independent expected pins. A branch/tag/latest label alone is not an immutable target.
- Exact native host/frontend/manager/SDK/tool/dependency versions and actual current configuration support receipts; upstream declared version requirements and primary compatibility contracts, including supported format/permissions/default changes and semantic loss.
- Accepted finite limits for sources/entries, raw/per-object/aggregate bytes, dependency depth, change rows, license documents, consumer cases, elapsed time and evidence age; approved audience/custody/recovery owner. No silent truncation of a full-review requirement.

Missing old base, local preservation, full required source bytes, new exact pin, applicable rights, version contract or authority blocks affected adoption. Finish independent comparison rather than fetching a convenient substitute or following current latest.

## Task

### 1. Bind all identities and preserve the old basis

1. Apply upstream-sync's identity and preservation sequence. Keep old upstream, current local baseline/effective customizations, old installed/distribution bytes, new upstream and proposed result distinct. A source commit is not the hash of an installed wrapper or archive; retain all actual transformations and source/output lineage.
2. Compare genuinely measured raw pins to independently accepted originals using existing permitted evidence/tools. A self-consistent digest shipped beside replaceable bytes does not authenticate a publisher. Required signatures/provenance use the actual existing verifier and accepted trust policy; absent proof remains BLOCKED.
3. Preserve old accepted source/package/trust records and authentic owner decisions. Do not refresh the expected pin because current bytes differ. Mark discrepancy, stale alias/tag resolution, mutable archive or unavailable exact bytes explicitly.
4. Establish current ownership and recoverable local state before any separately authorized change. Do not reset/stash/clean away user changes, edit managed output instead of its accepted source, or assume no local customization because upstream filenames match.

### 2. Expose the entire reviewable change

Use report-local rows tied to upstream-sync's three-way comparison, not a second import ledger:

| Component/path and old upstream/local/new exact identities | Complete incoming change + local customization | Rights/notices and authentic decision owner | Native version/dependency/permission impact | Accepted proposed result and affected consumers | Actual source/proof or gap | MET / NOT_MET / BLOCKED; next owner |
| --- | --- | --- | --- | --- | --- | --- |

1. Account for every added/modified/deleted path, moved/case-renamed component, mode/link/binary/LFS/submodule/generated content and newly bundled dependency in the accepted scope. Text diffs and release notes cannot stand in for opaque binary or omitted member review. Unsupported comparisons remain explicit blockers for a full-change claim.
2. Use old-upstream→local and old-upstream→new comparisons on the real import mapping. Record textual and semantic conflicts, including deleted extension points, changed defaults/permissions, wrappers, instructions, schemas, policy, templates, notices and cross-component consumers. A conflict-free merge is not behavioral acceptance.
3. Map each local customization to retain, adapt, authentically accepted replacement/supersession, conflict or unknown, with actual owner decision. Do not silently drop local restrictions or infer approval from the upstream maintainer's decision.
4. Re-evaluate rights for every affected component and intended use/recipient through license dossier, including new assets/dependencies, per-file terms, notice/source obligations and retained local adaptations. Source visibility, old rights or a risk waiver do not supply new redistribution rights. Preserve required notices in the actual proposed delivery.
5. Present the entire bounded change and exclusions so the owner can review it. A summary is useful only with full underlying accepted evidence. If scope is too large, the real owner must accept independently usable staged units under small-PR planning; do not claim the full new revision is installed after applying only a subset.

### 3. Review native compatibility, not only source pins

For every changed dependency/surface, bind old installed and proposed exact versions, upstream supported requirements, actual native host/client contract and known semantic losses. Include registration layout, supported metadata/schema, tool permissions/preapproval, connector/MCP/SDK contracts, model/deployment entitlement if relevant, and transitive version/lock requirements. Do not guess SDK methods, compatible version ranges or support from a version prefix.

Classify separately: source correspondence established; documented compatibility; installed/discovered; loaded/invoked; actual affected consumer behavior. Native availability/version support requires existing authentic observations, not a matching manifest or a successful file copy. Changed dependency graph/locks use dependency-upgrade with separately scoped authority; no automatic dependency installation, host enablement, signup or paid-plan change.

Frozen active/paused/archived jobs retain their exact accepted policy/schema/instruction/skill bytes and evidence. A new source pin never silently refreshes them. Apply the existing upgrade guide only under authentic separately authorized migration, preserving old baseline and invalidating affected proof. A frozen reference that cannot be recovered remains blocked, not silently replaced by the new version.

### 4. Separate decisions, update effects and consumer proof

The review returns a proposed exact target and complete conflict/rights/compatibility decisions. A separately authorized source owner uses upstream-sync to apply the accepted candidate while preserving local state. Rebuild/export, installer/manager update, native registration, consumer invocation and publication are distinct handoffs with exact bytes/targets/authority and actual receipts/readback; no assessment PASS grants the next step.

Require actual assigned consumer proof against the exact proposed/applied bytes: a preserved customization, changed upstream behavior, relevant failure/default path and notices in the delivered result. For Markdown, an authorized real consumer walkthrough can establish only its observed procedural scope; do not invent a runtime/model call. Existing plugin acceptance owns installed discovery/invocation/removal evidence. Unrun required proof stays BLOCKED.

### 5. Reconcile update failure without silent refresh

On pin drift, missing base, unresolved rights/customization, unexpected live writer, changed native requirement or failed consumer proof, hold affected adoption/install/publication. Preserve old records, exact failing bytes and independently completed rows. Actual update ambiguity is reconciled by native manager/operation and exact installed-version readback before retry. Restore only owned changes under separate recovery authority from the verified preserved baseline; code rollback cannot undo hooks, disclosure, remote effects or data migration. Never repin latest, overwrite managed output or rewrite frozen histories to repair the result.

## Constraints

No new updater, schema, ledger, generator, parser, wrapper, gate or runtime. No commands, Git/native/provider calls, fetch, installs, host enablement or credential discovery. Pin equality is not authenticity, rights, compatibility or actual update. Preserve all existing gate and independent review requirements; planned compatibility and source edits are not installed consumer proof.

## Format

Use the [response template](../../templates/response-template.md) or no-write chat: full old-upstream/local/installed/new/proposed identities and mappings; independent trust basis; complete change/customization/rights matrix; native exact-version/dependency impacts; authentic decisions and unresolved owners; separately requested versus performed effects/receipts; actual/NOT RUN consumer scope; retained frozen jobs and recovery. Include every criterion with MET/NOT_MET/BLOCKED, safe evidence retrieval/ACL/retention and invalidation conditions. Preserve the executing role verdict and distinguish assessment, proposed, applied/verified and published facts.

### Parent consumer cases — illustrative, NOT RUN

- A known old base, complete new immutable snapshot and local permission customization exist. Require the three-way row to preserve that restriction or cite authentic owner-approved replacement; no automatic upstream default wins.
- A tag changed and the new bundle contains an asset with unresolved rights and an unsupported host requirement. Do not update the expected digest or install to experiment; block the affected rights/native compatibility rows with exact owners.
- A new source pin is accepted for future jobs, while an active job uses a frozen old instruction snapshot. Keep the active job unchanged; a separate authentic upgrade/migration and invalidated-proof decision is necessary before any refresh.

# Accessible, localized consumer experience

Apply [domain review](../SKILL.md) through the existing UI, UX and i18n specialists, retaining independent reviews and their read-only source constraints. Automated accessibility results, screenshots and source inspection are complementary; none establishes complete accessibility or usability on unexercised assistive technology.

## Inputs

Obtain the changed consumer flows/design system, accepted accessibility target and applicable criteria, supported browser/device/OS/assistive-technology and locale matrix, real host/browser capabilities and product error/recovery requirements. Identify primary tasks and loading, empty, validation, denied, offline/timeout and success states. Record missing actual devices, screen readers or locales; emulation is not an actual-device observation.

## Sequence and decisions

1. Choose representative high-impact tasks and the supported surface matrix with scope rationale. In the actual browser/runtime inspect semantic controls, accessible names/roles/states, labels/instructions, reading/order structure and meaningful announcements. Check contrast and noncolor indicators using observed values. An ARIA attribute's presence does not prove correct behavior; prefer native semantics over custom widgets where appropriate.
2. Complete each task with keyboard alone: logical tab order, visible unobscured focus, operable controls, expected shortcuts and no trap. For modal/dialog flows verify initial focus, containment appropriate to the modal, accessible naming, background interaction/inertness, supported escape/cancel behavior and focus restoration to a meaningful trigger. Test nested/async closing and removed triggers; nonmodal content must not accidentally trap focus.
3. Exercise validation, server failure, timeout, loading and success. Associate field errors with controls; announce meaningful changes without repeated noise. Preserve valid input, avoid unexpected context changes, identify the next recovery action and make retry/cancel safe. Confirm disabled/pending UI does not falsely imply an operation never committed; reconcile ambiguous effects before consumer retry.
4. At supported zoom/text-scaling and narrow reflow conditions, verify content and controls remain readable/operable without clipping, overlap or unjustified two-axis scrolling. Use the accepted target's concrete sizes (for example, 200% text and 400% browser zoom or 320 CSS-pixel reflow when those criteria apply). Check touch target/gesture alternatives, orientation and reduced-motion preferences as applicable. Record viewport, scaling and any legitimate criterion exception rather than claiming universal responsiveness.
5. Use **actual** supported screen reader/assistive technology plus browser/OS versions for critical reading, form, modal and dynamic-state tasks when required. Capture sanitized task results and announcements without inventing transcripts. If only static/automated checks or browser accessibility trees are available, report those precisely; required manual AT coverage remains BLOCKED. Record other supported combinations not exercised and why.
6. For localization, inventory all visible and assistive text including errors, emails/exports when affected, plural/gender/select forms and fallback behavior. Verify translation-key completeness, interpolation/escaping, long-string expansion, bidirectional text/isolation, RTL reading/focus/layout and locale-aware dates/numbers/currency/time zones with the actual library/locale data. Distinguish locale from currency and display date from storage instant; do not silently change meaning at DST or month boundaries. Pseudolocalization detects layout risks, not translation accuracy; use qualified language review where required.
7. Review design-system consistency and actual task completion across selected supported browser/device combinations, including touch and keyboard differences. Identify actual hardware versus emulation. Tie findings to exact steps, expected/observed result, candidate and surface; automated clean output never waives an applicable independent UI/UX review.

## Evidence, failure and recovery

Deliver task/state/surface/locale matrix, target criteria, candidate and browser/device/AT versions, actual keyboard/focus/modal/zoom/reflow results, sanitized captures, automation scope and untested limitations. Missing required runtime/AT surface blocks its claim, not all unrelated analysis. On task-blocking defects or unsafe repeated effects, stop that path, preserve steps and request a builder fix. Re-exercise the failing task plus neighboring recovery/focus/locale paths on the corrected candidate; source-only inspection does not close a runtime finding. Remove only owned test accounts/data under authorization and retain accessible evidence with appropriate privacy.

## Consumer acceptance scenario

A keyboard and screen-reader user opens a localized checkout dialog, edits fields, encounters a server validation error, corrects it and completes the task. Focus enters/returns correctly, errors are associated and announced once, input is retained and no duplicate purchase occurs after a timeout. At the accepted zoom/reflow size the submit/cancel controls remain usable; a supported RTL locale preserves reading order and correctly formats the chosen currency/date. Record exactly which real AT/browser/device combinations exercised this scenario and which remain unproved.

# Maintain a verification skill

Keep a project-local ordinary verification skill honest as its application changes. This is not [maintain-formal-verification-skill](../maintain-formal-verification-skill/SKILL.md). Read [create-verification-skill](../create-verification-skill/SKILL.md) for the generation and proof contract. Scope edits to the target verification skill directory, its Markdown feature map and documented tool recipes. No product code, bundled runtime scripts, hidden fenced executables, automatic schedules, or global policy edits.

Apply [verification-strategy](../verification-strategy/SKILL.md) to accepted task-matrix rows in `decision.md`/`spec.md` before driving: retain requirement/invariant IDs, selected risk-based proof, actual fixtures/environment, limitations and exact evidence/invalidation dependencies. Maintaining every journey does not prove all integration/consumer/concurrency/load/formal obligations. Do not universally add those types, but keep required affected proofs and configured checks/code/security reviews. A focused maintenance request must name its subset and cannot claim full clean/changed coverage.

## Outcomes

- **clean:** every feature received source and live coverage; no correction worth shipping. No new branch or PR.
- **changed:** proven corrections to the verification instructions/map are complete. Publish at most one PR only if authorized and after the applicable GSF readiness gate; otherwise report changed, locally ready/unpublished.
- **blocked:** source or live coverage is incomplete, a regression prevents safe completion, or a proven correction cannot safely be finalized. Name the exact missing prerequisite and completed coverage. No PR advertising complete maintenance.

## Ordered pass

1. **Locate and authorize.** Discover existing `.gsf/skills/verify-*/` skills, including established alternate locations. A target must have Launch/Doctor/Drive/Evidence/Cleanup and a feature map. Use the named target; if several equally plausible targets remain, ask which. With none, point to create-verification-skill rather than inventing a target. Read scope and execution authority. If live driving is not permitted, do the reachable source work and report blocked rather than quietly converting the pass into a source-only success. A read-only inspection request must not initialize a job or write run notes.
2. **Index hygiene.** Read the map README and enumerate feature files. Reconcile missing, duplicate, extra, dead, or unlinked entries against actual files. No generated inventory/runtime is necessary. Record each feature's source status and live status in concise Markdown run evidence only where writes are authorized.
3. **Source wave.** After identifying shared entry points, use one concurrent read-only investigator per feature when delegation is available and worthwhile. Give each the feature file, source anchors, intended user result and scope. Each returns: feature summary; concrete source entry points; likely drift or none with citations; required fixture; one live recipe and expected predicate. Children never drive the app or edit. If delegation is unavailable, inspect the same features serially and disclose the limitation; do not claim an independent review or count it toward a required independent publication gate.
4. **Reconcile all features.** Account for every feature file, spot-check reported drift, and merge overlapping recipes into as few safe app states as practical. Sweep recent routes/commands/menus/docs churn for unmapped user-facing surfaces; require a concrete source path before calling one missing. Add confirmed omissions to the coverage set. Do not treat source agreement as live evidence.
5. **Live pass.** The coordinator alone drives every mapped feature at least once, including newly mapped features. Use the target lifecycle: one owned server/UI instance serially, or fresh isolated invocation/PTY per short-lived drive after one build. Doctor before first drive and each fresh session. Capture actual command/cwd or skill invocation, readiness predicate, candidate/policy/environment, fixture, loaded output digest and build-input/toolchain/config identity. Use canonical candidate collection and isolated external export/build manifests for large builds, never blanket ignored source inputs. Compare each configured `effect`/`target` to nested setup/drive/capture/cleanup effects; stale/unavailable required capability or mismatched target blocks affected work. External effects need authentic scoped grants and real safeguards. Capture surprises before reset; rerun Doctor and reset/relaunch owned state when needed. Never hijack user sessions or call source-text/mock-echo/forwarding checks live proof.
6. **Maintain safety and evidence.** Preserve action/result/side-effect proof, including failure and prerequisite gaps. Use configured evidence store/location/retention, exact index, actual retrieval identity, digest/content and ACL/retention/expiry observations; manual local retention is not enforced TTL. Missing/expired/denied/tampered evidence blocks dependent completion. Preserve proof outside teardown state and actually retrieve it after cleanup and cold resume. Clean only owned captured handles/sessions/fixtures after success or failure; preserve evidence and identify any residual resource with safe recovery. Never kill by name, delete unowned data or weaken a journey for missing seed.
7. **Triage before editing.** Wrong navigation, selectors, or obsolete descriptions with intended behavior demonstrably intact are **documentation/harness drift**. Correct them in scope using actual source and live evidence. An app no longer fulfilling its intended user result is a **product regression**, even if changing the map would make the pass green: preserve the intended predicate and report the reproduction and evidence; do not edit product code or normalize the failure into documentation. When intent is ambiguous, investigate with how/why and report the uncertainty instead of guessing. An unsupported driver is a **harness gap**; use existing host/repository tools, not a newly bundled script.
8. **Prove corrections.** Re-drive every corrected journey and any affected shared lifecycle step, capture its new predicate result, and run cleanup on failed iterations too. Re-read changed feature instructions before finalizing them. Full source and live coverage of all features is still required for clean/changed. A product gap may coexist with corrections, but must remain explicit; if it prevents completing coverage, the outcome is blocked.
   Apply verification-strategy's invalidation matrix to changed source, policy/instructions, check/toolchain/config/dependencies, fixture/schema/auth, artifact/target/expiry and evidence integrity. A prior result can be reused only with exact immutable receipt/provenance/dependency equality and current retrieval proof; identify it as reused, never newly executed. Because this maintenance procedure requires a fresh live pass of every mapped feature, reuse of supporting unchanged evidence does not waive step 5. Matching HEAD/command or a previous badge is insufficient.
9. **Finish once.** For clean, report no changes and no PR. For changed, hand off one coherent correction set with proof and publication authorization status; never publish a failed candidate. For blocked, leave safe diagnostic evidence and report covered/uncovered features, product regressions, access/readiness limits and any owned resources needing recovery. Do not make an unrelated product fix or a broad source refactor.

## Report

Lead with clean / changed / blocked. Give feature-by-feature source/live coverage, newly executed/reused/NOT RUN/BLOCKED proof, risk/requirement coverage and uncovered domains, drift/correction paths, product regressions separately, capability/readiness gaps, candidate/policy/build/config/environment identity, actual invocation/artifact evidence, retrieval/retention/expiry status, teardown result and any authorized PR link. Keep private transcripts/credentials out of public reports. Durable job proof follows canonical contracts; a Markdown procedure is neither atomic executor nor sandbox/exactly-once guarantee.
